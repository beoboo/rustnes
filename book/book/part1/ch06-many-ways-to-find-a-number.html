Build Your Own NES Emulator

Many ways to find a number

LDA #10 puts ten into A. Lovely — if the program already knows it wants ten. But games mostly want numbers that live somewhere: the hero’s health, the current score, which door is locked. Those sit in memory, at addresses, and instructions need ways of saying where to look.

The 6502 has eight ways, called addressing modes, and LDA speaks all of them. Today we build all eight — once, in one place — and by the end, a value will leave A, hide in memory, and come back on command.

One instruction, many flavors

“LDA”, it turns out, is not one opcode. Each flavor gets its own:

opcodewritten aswhere the value lives
A9LDA #42right after the opcode
A5LDA $10at address $0010
ADLDA $0234at address $0234

…and five more we’ll meet in a minute. The CPU never guesses: the opcode itself says which finding-method to use. Our step function will do the same — but if we wrote the finding-code eight times inside LDA, we’d have to write it eight times again for STA, and for ADC in chapter 7, and on and on. The 6502 reuses these modes everywhere, so we will too: one function that answers one question — where?

Naming the flavors

A fixed menu of choices is exactly what Rust’s enum is for. Add this to cpu.rs, right after the flag constants:

src/cpu.rs

/// The ways an instruction can say WHERE its value lives.
/// (`Clone, Copy` lets us hand modes around as freely as numbers.)
#[derive(Clone, Copy)]
pub enum AddressingMode {
    /// The value sits right after the opcode, in the program itself.
    Immediate,
}

One entry so far — Immediate, the flavor we already know. The menu grows as this chapter goes.

Now the question-answerer. It returns the address where the value waits, and moves PC past whatever bytes the mode used. Into the impl Cpu block, after reset:

src/cpu.rs

    // where its program begins. The CPU's first act is to read it.
    self.pc = self.read_word(0xFFFC);
}

/// Where does this instruction's value live? Every addressing mode
/// answers differently. This function does the finding, and moves PC
/// past whatever bytes the mode used up.
fn operand_address(&mut self, mode: AddressingMode) -> u16 {
    match mode {
        // The value's address IS where PC points. Note it, step past.
        AddressingMode::Immediate => {
            let address = self.pc;
            self.pc = self.pc.wrapping_add(1);
            address
        }
    }
}

/// Run ONE instruction: fetch it, decode it, execute it.
/// Returns `false` when the program says stop, `true` otherwise.

Look at the Immediate arm closely — it’s slightly sneaky. The value sits right where PC points, so its address… is PC. We note the address, hop over the value, done. Even “the value is right here” is just an address.

The fast lane

The first 256 addresses — $0000 to $00FF — are called the zero page, and the 6502 treats them as its favorite shelf. Naming one takes a single byte instead of two, which makes the instruction shorter and, on real hardware, faster. 6502 programmers guard their zero page like treasure.

Two new menu entries — add them to the enum, under Immediate:

src/cpu.rs

pub enum AddressingMode {
    /// The value sits right after the opcode, in the program itself.
    Immediate,
    /// One byte names an address in the first 256 — the "zero page".
    ZeroPage,
    /// Zero page, then add X.
    ZeroPageX,

And their finding-code, in operand_address, after the Immediate arm:

src/cpu.rs

    self.pc = self.pc.wrapping_add(1);
    address
}
// One byte, naming one of the first 256 addresses.
AddressingMode::ZeroPage => {
    let address = self.read(self.pc) as u16;
    self.pc = self.pc.wrapping_add(1);
    address
}
// Zero page plus X — and the sum wraps WITHIN the page:
// $FF + 2 lands on $01, never on $101.
AddressingMode::ZeroPageX => {
    let base = self.read(self.pc);
    self.pc = self.pc.wrapping_add(1);
    base.wrapping_add(self.x) as u16
}

ZeroPageX is the list-reading flavor: the program names a starting spot, X picks which entry. And note its little rule: base plus X wraps within the page — $FF + 2 lands on $01, never $101. The zero page is a circle, not a line. Our test will prove it.

(There’s a Y twin, ZeroPage,Y. Exactly one instruction uses it, and it arrives in chapter 9 — no point stocking a shelf nobody shops from yet.)

Anywhere at all

For everywhere else there’s absolute mode: a full two-byte address, little end first — your read_word from chapter 4 has been waiting for this moment. Three menu entries:

// Two bytes, little end first — a full address.
AddressingMode::Absolute => {
    let address = self.read_word(self.pc);
    self.pc = self.pc.wrapping_add(2);
    address

// Absolute plus X: perfect for "element X of a list".
AddressingMode::AbsoluteX => {
    let base = self.read_word(self.pc);
    self.pc = self.pc.wrapping_add(2);
    base.wrapping_add(self.x as u16)
}
// The same, with Y.
AddressingMode::AbsoluteY => {
    let base = self.read_word(self.pc);
    self.pc = self.pc.wrapping_add(2);
    base.wrapping_add(self.y as u16)
}

Absolute,X and Absolute,Y are how games walk through lists anywhere in memory: “the table starts at $0200; give me entry X.” When a game draws a row of enemies, something very like this is running.

Follow the pointer

Now the strangest and most powerful flavor. Sometimes a program can’t say the address in advance, because the address itself is data — computed while the game runs, stored in memory like any other value. A stored address has a name: a pointer.

The parentheses say everything: don’t stop at $20 — follow what you find there. And here’s why that changes everything: the pointer is two bytes of ordinary, writable memory. The program can re-aim it while running — at this level’s map now, at the next level’s later — and the same LDA serves both without changing a single instruction. Every “current thing” a game has (current level, current song, current enemy list) is somewhere downstream of a pointer like this one.

Last two menu entries:

src/cpu.rs

    AbsoluteX,
    /// Absolute, then add Y.
    AbsoluteY,
    /// ($xx,X): add X to a zero-page spot; a POINTER waits there.
    IndirectX,
    /// ($xx),Y: a pointer waits at a zero-page spot; add Y afterwards.
    IndirectY,
}

And their arms — each one is just moves you already know, chained:

src/cpu.rs

            self.pc = self.pc.wrapping_add(2);
            base.wrapping_add(self.y as u16)
        }
        // ($xx,X): add X to the zero-page spot, THEN follow the
        // pointer stored there.
        AddressingMode::IndirectX => {
            let base = self.read(self.pc);
            self.pc = self.pc.wrapping_add(1);
            let pointer = base.wrapping_add(self.x) as u16;
            self.read_word(pointer)
        }
        // ($xx),Y: follow the pointer at the zero-page spot, THEN
        // add Y to wherever it led.
        AddressingMode::IndirectY => {
            let base = self.read(self.pc) as u16;
            self.pc = self.pc.wrapping_add(1);
            self.read_word(base).wrapping_add(self.y as u16)
        }
    }
}

The difference between the two is when the register joins in. ($xx,X): add X first, then follow. ($xx),Y: follow first, then add Y. The second one is everywhere in real games — “the current level’s data, entry Y” — and the first is its rare cousin. If this section needed two reads, that’s normal. It’s the hardest idea in the chapter, and it’s downhill from here.

Rewiring LDA

Time to spend all this. First, a small ceremony: delete the old LDA arm — the whole 0xA9 => { ... } block in step, from chapter 5, flag-note line and all. It served well for one chapter. This is the first time the book replaces code you typed, and it won’t be the last; building software means outgrowing your own earlier work, on purpose, without sentimentality.

In its place, LDA becomes a one-liner per flavor. First the worker — into the impl block, right after step:

src/cpu.rs

    true
}

/// LDA, any flavor: find the value, load it into A, take notes.
fn lda(&mut self, mode: AddressingMode) {
    let address = self.operand_address(mode);
    self.a = self.read(address);
    self.update_zero_and_negative(self.a);
}

Find, load, take notes: the same three moves as always, but the finding is delegated. Now the new arms, where the old LDA arm used to be:

src/cpu.rs

// DECODE and EXECUTE: recognize the opcode, do what it says.

    0xB9 => self.lda(AddressingMode::AbsoluteY),
    0xA1 => self.lda(AddressingMode::IndirectX),

Eight flavors, eight lines. And since storing is loading’s mirror, A’s way back to memory costs almost nothing now. The worker — right after lda:

/// STA, any flavor: find the address, store A there.
/// No flags — storing changes memory, not the CPU's mood.
fn sta(&mut self, mode: AddressingMode) {
    let address = self.operand_address(mode);
    self.write(address, self.a);
}

/// Almost every instruction ends the same way: the CPU looks at the
/// value it just produced and updates two flags about it.

A round trip through memory

The demo program deserves an upgrade. Replace the comment table and the program line inside cpu_demo (in main.rs) with:

src/main.rs

/// Load a little machine-code program, wake the CPU, run it to the end,
/// and print every pocket after every instruction.
fn cpu_demo() {
    // A value takes a round trip through memory: into address $0010,
    // then A is wiped clean, then the value comes back.
    //
    // bytes    meaning
    // A9 2A    LDA #42    put 42 into A
    // 85 10    STA $10    store A at address $0010
    // A9 00    LDA #0     wipe A clean
    // A5 10    LDA $10    bring the 42 back
    // 00       BRK        stop
    let program = [0xA9, 0x2A, 0x85, 0x10, 0xA9, 0x00, 0xA5, 0x10, 0x00];

    let mut cpu = Cpu::new();

cargo run:

  ---------------

  8009   2A 00 00
  (BRK: the program is done)

Watch A’s column: 2A (42 arrives), 2A (stored — A keeps its copy), 00 (wiped clean), 2A — back from the dead. The value survived outside the CPU, in memory, and LDA’s zero-page flavor fetched it home. Every game you’ve ever played is this trick, performed a few million times per second.

Did it work?

The modes need something to find, so the robots get a new helper that plants values in memory before running. Add these inside the tests module, after the chapter 5 tests:

src/cpu.rs

        assert_eq!(cpu.x, 0);
        assert!(cpu.status & FLAG_ZERO != 0);
    }

    /// Like `run_program`, but first plant some values in memory —
    /// the addressing modes need something to find.
    fn run_program_with(program: &[u8], plants: &[(u16, u8)]) -> Cpu {
        let mut cpu = Cpu::new();
        for (i, byte) in program.iter().enumerate() {
            cpu.write(0x8000 + i as u16, *byte);
        }
        for (address, value) in plants {
            cpu.write(*address, *value);
        }
        cpu.write(0xFFFC, 0x00);
        cpu.write(0xFFFD, 0x80);
        cpu.reset();

        while cpu.step() {}
        cpu
    }

    #[test]
    fn lda_zero_page_reads_from_the_first_page() {
        // LDA $10 — the byte planted at $0010 lands in A.
        let cpu = run_program_with(&[0xA5, 0x10, 0x00], &[(0x0010, 0x2A)]);
        assert_eq!(cpu.a, 0x2A);
    }

    #[test]
    fn lda_zero_page_x_wraps_inside_the_page() {
        // X = 2 (via TAX), then LDA $FF,X — $FF + 2 wraps to $01.
        let cpu = run_program_with(&[0xA9, 0x02, 0xAA, 0xB5, 0xFF, 0x00], &[(0x0001, 0x77)]);
        assert_eq!(cpu.a, 0x77);
    }

    #[test]
    fn lda_absolute_reads_anywhere() {
        // LDA $0234.
        let cpu = run_program_with(&[0xAD, 0x34, 0x02, 0x00], &[(0x0234, 0x55)]);
        assert_eq!(cpu.a, 0x55);
    }

    #[test]
    fn lda_absolute_x_adds_x() {
        // A = X = 5 via TAX, then LDA $0200,X reads $0205.
        let cpu = run_program_with(
            &[0xA9, 0x05, 0xAA, 0xBD, 0x00, 0x02, 0x00],
            &[(0x0205, 0x11)],
        );
        assert_eq!(cpu.a, 0x11);
    }

    #[test]
    fn lda_absolute_y_adds_y() {
        // The test sets Y by hand — robots may reach anywhere.
        let mut cpu = Cpu::new();
        for (i, byte) in [0xB9, 0x00, 0x02, 0x00].iter().enumerate() {
            cpu.write(0x8000 + i as u16, *byte);
        }
        cpu.write(0x0205, 0x66);
        cpu.write(0xFFFC, 0x00);
        cpu.write(0xFFFD, 0x80);
        cpu.reset();
        cpu.y = 5;
        while cpu.step() {}
        assert_eq!(cpu.a, 0x66);
    }

    #[test]
    fn lda_indirect_x_adds_x_then_follows_the_pointer() {
        // X = 4 via TAX; ($1C,X) means the pointer waits at $20,
        // and the pointer says $0300.
        let cpu = run_program_with(
            &[0xA9, 0x04, 0xAA, 0xA1, 0x1C, 0x00],
            &[(0x0020, 0x00), (0x0021, 0x03), (0x0300, 0x88)],
        );
        assert_eq!(cpu.a, 0x88);
    }

    #[test]
    fn lda_indirect_y_follows_the_pointer_then_adds_y() {
        // The pointer at $20/$21 says $0300; Y adds 4; $0304 holds the prize.
        let mut cpu = Cpu::new();
        for (i, byte) in [0xB1, 0x20, 0x00].iter().enumerate() {
            cpu.write(0x8000 + i as u16, *byte);
        }
        cpu.write(0x0020, 0x00); // pointer, little end
        cpu.write(0x0021, 0x03); // pointer, big end
        cpu.write(0x0304, 0x99);
        cpu.write(0xFFFC, 0x00);
        cpu.write(0xFFFD, 0x80);
        cpu.reset();
        cpu.y = 4;
        while cpu.step() {}
        assert_eq!(cpu.a, 0x99);
    }

    #[test]
    fn sta_stores_a_into_memory() {
        // LDA #$42, STA $0250.
        let cpu = run_program(&[0xA9, 0x42, 0x8D, 0x50, 0x02, 0x00]);
        assert_eq!(cpu.read(0x0250), 0x42);
    }
}

Two tests do something new: they set cpu.y by hand, because no instruction can load Y until chapter 9. That’s allowed — tests may reach into places programs can’t. Robots have long arms.

For the curious

Why is zero page genuinely faster on the real chip? Because every byte of an instruction takes one clock tick to fetch. LDA $10 is two bytes; LDA $0010 written absolutely is three. Same address, one tick slower — and in a game drawing 60 pictures a second, ticks are money. Memory is sliced into 256-byte pages ($0000–$00FF is page zero, $0100–$01FF page one, and so on); crossing from one page to another mid-count has its own costs, which becomes a whole story in Part II.
