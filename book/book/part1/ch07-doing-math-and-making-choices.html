Build Your Own NES Emulator

Doing math and making choices

Our CPU can fetch, carry things around, and count on one finger. Today it learns to compute — add, subtract, compare — and then the big one: to choose. By the last page, your emulator runs its first loop, and a loop is the moment a program stops being a to-do list and starts being a machine.

Adding

The 6502 has exactly one addition instruction: ADC, “ADd with Carry” — we’ll get to the Carry part in a moment. It adds a value into A, and it comes in the same eight flavors as LDA, which means operand_address is about to pay for itself again.

First, a new flag. Add it above FLAG_ZERO, at the top of cpu.rs:

src/cpu.rs

    pub memory: [u8; 65536],
}

/// The Carry flag: the ninth bit of the last addition — and, for
/// subtraction and comparing, the "no borrow needed" signal.
pub const FLAG_CARRY: u8 = 0b0000_0001;

/// The Zero flag: switched on when the last value the CPU handled was zero.
pub const FLAG_ZERO: u8 = 0b0000_0010;

Here’s why. Add 200 + 100 in a pocket that only holds 0 to 255: the true answer, 300, needs a ninth bit, and the pocket has eight. The 6502 doesn’t panic and doesn’t lie — it keeps the eight bits it can (300 wraps to 44) and drops the ninth bit into the Carry flag. Nothing is lost; the extra bit is just… carried. Exactly what you do on paper when a column overflows: write the 4, carry the 1.

The worker and its helper — into the impl block, after sta:

/// ADC — ADd with Carry: the 6502's one and only addition.
fn adc(&mut self, mode: AddressingMode) {
    let address = self.operand_address(mode);
    let value = self.read(address);
    self.add_to_a(value);
}

/// The shared heart of addition and subtraction: add a value into A
/// and take all the notes.
fn add_to_a(&mut self, value: u8) {
    let sum = self.a as u16 + value as u16;
    // The answer's ninth bit doesn't fit an 8-bit pocket:
    // it lands in the Carry flag.
    if sum > 0xFF {
        self.status |= FLAG_CARRY;
    } else {
        self.status &= !FLAG_CARRY;
    }

    let result = sum as u8;
    self.a = result;
    self.update_zero_and_negative(self.a);
}

Carrying in

So Carry catches what falls out of an addition. The other half of the trick: ADC also adds the Carry in. That’s not a quirk; it’s what the name has been telling you all along. Watch what it buys: to add two 16-bit numbers with an 8-bit CPU, you add the low bytes (the ninth bit lands in Carry), then add the high bytes — and the Carry walks right in as the “carry the 1”. Any size of number, eight bits at a time. Scores, timers, prices in games bigger than 255: all of them are this.

The habit every 6502 programmer has tattooed somewhere: CLC before you add, SEC before you subtract. Subtract? Patience — two sections.

Numbers below zero

Time to pay a debt from chapter 5: why does the top bit mean negative?

A pocket holds 256 different patterns. Nobody says they have to mean 0 to 255 — that’s just one way to read them. The 6502’s other way: patterns starting with 0 mean 0 to 127, and patterns starting with 1 mean -128 to -1. So $FF is 255 in one reading and -1 in the other. This scheme is called two’s complement1, and its magic is that the CPU doesn’t care which reading you meant. Adding works identically either way: 4 + $FF wraps to 3, and 4 + (-1) is 3. Same bits, same circuit, two stories. The top bit tells you which side of zero you’re on in the signed story — and that’s what the N flag has been copying all along.

One accident is possible, though. Add 80 + 80: the true answer 160 doesn’t fit in -128..127, so its bit pattern starts with a 1 — two positive numbers “added up to” a negative. The Carry can’t see this (nothing fell out of the ninth bit); it’s a purely signed-story accident, so it gets its own flag:

src/cpu.rs

/// last value the CPU handled.

/// zero — a signed-arithmetic accident the Carry can't see.
pub const FLAG_OVERFLOW: u8 = 0b0100_0000;

Subtraction in disguise

Now the payoff of all that theory. The 6502 has SBC, “SuBtract with Carry” — and internally, it isn’t a second math circuit. Subtracting a number is just adding its negative, and in two’s complement, “make it negative” is: flip every bit, add one. So SBC flips the bits and calls the addition we already have — and the “+1”? It walks in through the Carry. That’s why the ritual is SEC-then-subtract: the set Carry is the plus-one of the disguise.

In code, the flip is value ^ 0xFF: xor against all-ones turns every bit around. Which makes our SBC four lines. After add_to_a:

src/cpu.rs

    self.a = result;
    self.update_zero_and_negative(self.a);

/// SBC — SuBtract with Carry. Subtraction is addition in disguise:
/// flip every bit of the value and add it. The missing "+1" of the
/// disguise comes in through the Carry — which is why every fresh
/// subtraction starts with SEC.
fn sbc(&mut self, mode: AddressingMode) {
    let address = self.operand_address(mode);
    let value = self.read(address);
    self.add_to_a(value ^ 0xFF);
}

Afterwards, Carry doubles as the borrow report: still set means “no borrow was needed” (the answer didn’t dip below zero); clear means the subtraction wrapped. The tests will show both.

Comparing

“Is the score 100 yet?” “Is the hero’s X past the edge?” Games ask constantly, and the 6502 answers with CMP: a subtraction that throws away the answer and keeps only the notes. A stays untouched; the flags report. Zero set: they were equal. Carry set: A was greater or equal. That’s the entire trick — and X and Y get their own versions, CPX and CPY. The worker, after sbc:

src/cpu.rs

    let value = self.read(address);
    self.add_to_a(value ^ 0xFF);
}

/// CMP — CoMPare A — with CPX and CPY for the other pockets: a
/// subtraction that throws the answer away and keeps only the
/// notes. Carry means "no borrow was needed" — in other words,
/// register >= value.
fn compare(&mut self, mode: AddressingMode, register: u8) {
    let address = self.operand_address(mode);
    let value = self.read(address);

    if register >= value {
        self.status |= FLAG_CARRY;
    } else {
        self.status &= !FLAG_CARRY;
    }
    self.update_zero_and_negative(register.wrapping_sub(value));
}

Going somewhere else

Until now, PC has only ever marched forward. But PC is just a pocket — and JMP writes a new address straight into it. One arm, after the compare block:

src/cpu.rs

0xC4 => self.compare(AddressingMode::ZeroPage, self.y),
0xCC => self.compare(AddressingMode::Absolute, self.y),

// JMP — JuMP: put a new address straight into PC. That is
// all "going somewhere else" ever was.
0x4C => self.pc = self.operand_address(AddressingMode::Absolute),

That’s all of it. Next fetch, the CPU simply finds itself elsewhere and carries on, none the wiser. Every level select, every “PRESS START”, every menu is somewhere downstream of this one move.

Choosing

JMP always jumps. The branch family jumps if — and this is where the flags cash out. BEQ: branch if the Zero note says “equal”. BNE: if not equal. BCS/BCC ride the Carry, BPL/BMI the sign, BVS/BVC the Overflow.

Branches don’t carry a full address. They carry a one-byte offset: “hop this far from here” — and it’s a signed byte, our new friend two’s complement, so backwards is just a negative hop. (Why so stingy? A branch is the most common instruction in any program; making it two bytes instead of three saves memory everywhere and, on the real chip, time. There’s a cost: a branch can only reach 127 forward or 128 back. Games learn to live inside that.)

/// The heart of every branch: maybe move PC, by a SIGNED offset.
/// (`as i8` reads the byte as -128..=127; the second `as` stretches
/// it back to 16 bits, minus sign and all.)
fn branch_if(&mut self, condition: bool) {
    let offset = self.read(self.pc) as i8;
    self.pc = self.pc.wrapping_add(1);

    if condition {
        self.pc = self.pc.wrapping_add(offset as u16);
    }
}

/// Almost every instruction ends the same way: the CPU looks at the
/// value it just produced and updates two flags about it.

A real loop

Everything joins hands now. Replace the demo program in cpu_demo (comment table and program line) with:

src/main.rs

/// Load a little machine-code program, wake the CPU, run it to the end,
/// and print every pocket after every instruction.
fn cpu_demo() {
    // A program that goes BACKWARDS: count X up to three, by looping
    // over the same instructions.
    //
    // bytes    meaning
    // A9 00    LDA #0     start A at zero
    // AA       TAX        X = 0 too
    // E8       INX        add 1 to X          <-- $8003, the loop target
    // E0 03    CPX #3     is X 3 yet?
    // D0 FB    BNE -5     not yet? back to INX
    // 00       BRK        done: stop
    let program = [0xA9, 0x00, 0xAA, 0xE8, 0xE0, 0x03, 0xD0, 0xFB, 0x00];

    let mut cpu = Cpu::new();

That FB is -5, written as a byte. cargo run:

Read the pc column: 8004, 8006, back to 8003. Again. Again. The program is running in a circle, and each lap X climbs — until CPX raises the Zero note, BNE declines to jump, and the program falls out the bottom to BRK.

You’ve seen this shape before: while cpu.step() {} — the loop in our own Rust. Every language you will ever use is doing this underneath: a comparison writing notes, and a conditional jump reading them. Your emulator now contains the thing it is written in.

For the curious

The overflow spell, unrolled: a ^ result has its top bit set when A and the answer disagree about sign; value ^ result likewise for the value. Overflow is exactly “the answer disagrees with BOTH inputs” — two numbers on one side of zero can’t honestly land on the other. The & 0x80 keeps only the sign bit of all that. Three xors, one and: cheaper than any if-chain, and precisely what the real chip’s silicon computes.

  1. Picture the 256 patterns on a wheel, like a clock face: 0, 1, 2, … 255, and then back to 0 — the same wrapping our pockets have had since chapter 5. Stand at 0 and step backwards: you land on 255. So 255 behaves exactly like -1, 254 like -2, and in general -n sits at position 256 - n. Nobody decreed that; the wheel’s shape forces it. The scheme is just an agreement to read the wheel’s top half (128–255) as -128 to -1.

    The flip-the-bits trick follows: flipping every bit of n gives 255 - n (try it: 0000_0011 flips to 1111_1100, and 3 + 252 = 255); adding one gives 256 - n, the wheel’s position for -n. That’s SBC’s whole disguise — and the name: the complement to two-to-the-eighth (256), two’s complement. Check it against the subtraction test: 4 - 9 printed $FB = 251 = 256 - 5. Five steps back from zero: there’s your -5. ↩

  2. ^ is xor, “exclusive or” — the fourth bit tool, joining <<, |, and &. It compares two values bit by bit and answers 1 wherever they disagree, 0 wherever they agree. So a ^ b lights up exactly the bits where a and b differ — handy for “did the sign bit change?”. And xor-ing against a 1 always flips: a 0 disagrees with it, a 1 agrees — which is why x ^ 0xFF, all ones, flips every bit of x. Chapter 3’s bit tools section has the full kit. ↩
