Build Your Own NES Emulator

The picture chip

Chase is still spinning, asking $2002 whether the TV is ready. Time to start building the thing it’s talking to: the PPU — Picture Processing Unit — the second chip in the gray box, and the one this half of the book belongs to. We won’t finish it today. But by the last page, your window will stop showing a test pattern and start showing something no test could fake: the game’s actual art.

A second brain

The PPU is not a helper of the CPU. It’s a second computer on the board, with its own job — drawing, sixty times a second — and, remarkably, its own memory in its own address space:

When the CPU says “address $0000,” the bus hands it RAM. When the PPU says “address $0000,” a completely different set of wires hands it the cartridge’s CHR ROM. Same numbers, different world — which is why chapter 10 could claim, straight-faced, that CHR isn’t wired to the CPU at all. The two chips share nothing but a few doorbell registers (that’s the $2002 Chase keeps ringing) and the cartridge sitting between them.

This chapter needs only the bottom half of that map: the pattern tables, where tiles live.

Pictures from squares

The PPU cannot draw a pixel wherever it likes. Every picture it will ever make is assembled from tiles — 8×8 pixel squares — like a mosaic, or stickers on a grid. The background is tiles. The hero is tiles. The letters in “GAME OVER” are tiles. That faint grid you drew back in chapter 2 was this fact, foreshadowed: 32 tiles across, 30 down, and nothing on a NES screen ever happens outside that scheme.

It sounds like a limitation, and it is — but it’s the load-bearing kind. It’s why 8 KiB of CHR can hold a whole game’s art, and (in Part II) it’s why the PPU can keep up with the TV at all.

Two bits per pixel

So how does a tile store its 64 pixels? With shameless thrift: two bits per pixel — each pixel is just a number from 0 to 3. Sixteen bytes per tile, laid out in a scheme worth a picture:

A tile’s sixteen bytes are two bit-planes: the first eight bytes carry every pixel’s low bit (one byte per row, bit 7 leftmost), the second eight carry every pixel’s high bit. To read one pixel you visit both planes, pluck the same bit from each, and stack them. Why store it sideways like this instead of two clean bits together? Because the chip reads a whole row of low bits in one byte-fetch and a whole row of high bits in the next — the format is shaped like the hardware’s appetite, a Part II story with a chapter of its own.

And what does a pixel value of 2 look like? No idea — and neither does the tile. 0 to 3 aren’t colors; they’re crayon numbers, waiting for a palette to give them meaning. That’s chapter 14. Today we’ll use four grays and like it.

Create src/ppu.rs. Its first resident is the decoder — pure bit-tools from chapter 3, earning their keep:

src/ppu.rs

//! The picture chip — built here, piece by piece, starting with the
//! part every picture is made of: tiles.

/// Decode one tile: 16 bytes of CHR become 8x8 pixels of 0..=3.
///
/// A tile's first 8 bytes are plane 0 (every pixel's low bit, one byte
/// per row), its second 8 are plane 1 (the high bits). Bit 7 is the
/// leftmost pixel.
pub fn decode_tile(chr: &[u8], tile: usize) -> [[u8; 8]; 8] {
    let start = tile * 16;
    let mut pixels = [[0u8; 8]; 8];

    for row in 0..8 {
        let plane0 = chr[start + row];
        let plane1 = chr[start + row + 8];

        for col in 0..8 {
            let bit = 7 - col;
            let low = (plane0 >> bit) & 1;
            let high = (plane1 >> bit) & 1;
            pixels[row][col] = (high << 1) | low;
        }
    }
    pixels
}

NES art, in its entirety: sixteen bytes in, sixty-four little numbers out.

/// Draw every tile in CHR ROM, in four grays: pattern table 0 on the
/// left, pattern table 1 on the right. The game's whole sticker album.
fn draw_pattern_tables(chr: &[u8], buffer: &mut [u32]) {
    // The four pixel values, darkest to lightest.
    const GRAYS: [u32; 4] = [0x0000_0000, 0x0055_5555, 0x00AA_AAAA, 0x00FF_FFFF];

    for table in 0..2 {
        for tile in 0..256 {
            let pixels = ppu::decode_tile(chr, table * 256 + tile);

            // Sixteen tiles to a row; the second table starts 128
            // pixels to the right; 56 centers it all vertically.
            let corner_x = table * 128 + (tile % 16) * 8;
            let corner_y = 56 + (tile / 16) * 8;

            for row in 0..8 {
                for col in 0..8 {
                    let color = GRAYS[pixels[row][col] as usize];
                    buffer[(corner_y + row) * WIDTH + corner_x + col] = color;
                }
            }
        }
    }
}

The moment:

$ cargo run roms/Chase.nes

The boot trace scrolls past, the window opens — and there it is, in four grays: Chase’s entire character set marching by in ASCII order — punctuation, digits, the alphabet — then little interface pieces, then… chunky nonsense? Those jumbled slabs are the game’s big art — title letters, large shapes — sliced into 8×8 tiles and shelved in album order, which owes nothing to screen order. Every bit of it was extracted from bytes by your decoder. And notice the two halves nearly match: the left is pattern table 0, the right is table 1, and authors often stock both with the same art, since one table usually serves the background and the other the sprites.

(Boot Lan Master too. Different album — “PD2011 Shiru” on an actual shelf — same scheme.)

Two small confessions before we celebrate too hard. The tiles are gray because palettes don’t exist yet — chapter 14. And they’re in album order, not game order: nobody has told us which tile goes where on screen. That arrangement is the nametable, it lives in the PPU’s memory at $2000, and the only way to see a real one is to let the game write it — which needs those doorbell registers. Chapters 14 and 15, and then the title screen.

Did it work?

The robots learn to read art — at the bottom of ppu.rs:

src/ppu.rs

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn a_hand_drawn_row_decodes() {
        // Row 0: plane 0 = $55, plane 1 = $33 — reading the bits down
        // the columns should give 0,1,2,3 repeating.
        let mut chr = vec![0u8; 16];
        chr[0] = 0x55;
        chr[8] = 0x33;

        let pixels = decode_tile(&chr, 0);
        assert_eq!(pixels[0], [0, 1, 2, 3, 0, 1, 2, 3]);
        assert_eq!(pixels[1], [0; 8]); // every other row stayed blank
    }

    #[test]
    fn tiles_are_sixteen_bytes_apart() {
        // A single low bit at the start of tile 1, nowhere near tile 0.
        let mut chr = vec![0u8; 32];
        chr[16] = 0b1000_0000;

        let pixels = decode_tile(&chr, 1);
        assert_eq!(pixels[0][0], 1);
        assert_eq!(decode_tile(&chr, 0)[0][0], 0);
    }
}

The first test hand-builds a row where the planes disagree in every combination — 0,1,2,3 — the same drill as the figure. cargo test: sixty-two green.

Try it

  • The figure’s heart is real data: plane 0 is 00 00 66 7E 7E 3C 18 00, plane 1 is 00 66 9D 89 81 42 24 18. Poke those sixteen bytes into a test, decode, and check row 3 against the picture.
  • Find the letter A in the album, count rows of sixteen, and compute its tile number. Then the sneaky one: the two tables are almost identical — spot a difference.
  • Make the viewer draw value 0 as a loud pink instead of black. Suddenly you can see which parts of every tile are empty — that’s transparency, and it matters next chapter.

For the curious

Why two planes and not, say, four bits per pixel? Count the cost: 2 bits × 64 pixels = 16 bytes per tile, 512 tiles in 8 KiB. At 4 bits, half the tiles — for a machine whose games needed every sticker they could get. The palette system (next chapter) is the other half of the trick: few bits per pixel, but many meanings per value. Thrift stacked on thrift, and it’s about to get colorful.
