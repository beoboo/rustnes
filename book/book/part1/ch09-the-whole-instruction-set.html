Build Your Own NES Emulator

The whole instruction set

Time to finish the job. The 6502 understands 151 instructions; after four chapters of careful building, we own 64 of them — and, better, we own all the machinery: addressing modes, flags, the stack. Today the rest arrive in one sweep, and you’ll find that almost nothing new has to be invented. The CPU is a very repetitive machine. This chapter is where that repetition becomes your friend.

How many are left?

The territory, one cell per opcode:

Before counting cells, notice the map has architecture. Read down almost any column and the same names march in step — one instruction, returning in flavor after flavor. That’s because an opcode isn’t an arbitrary number: it’s a tiny packed structure, a few bits saying what and a few bits saying where, and the chip decodes the fields, not the byte. It’s also why the red is cheaper than it looks — mostly old friends in new flavors, falling to machinery we already own.

Counting in memory

INC and DEC count directly in a memory cell — no pocket involved. They’re our first read-modify-write instructions: fetch the value, change it, put it back. And since a whole family of instructions ahead shares that exact shape, we’ll build the shape itself, once.

Meet a new Rust idea doing it — into the impl block, after sty:

src/cpu.rs

    let address = self.operand_address(mode);
    self.write(address, self.y);
}

/// Read-modify-write: fetch a value from memory, hand it to a worker
/// function, store the worker's answer back where the value came
/// from. The worker is a PARAMETER — in Rust, a plain function's
/// name is a value you can pass around, like any other.
fn modify(&mut self, mode: AddressingMode, worker: fn(&mut Cpu, u8) -> u8) {
    let address = self.operand_address(mode);
    let value = self.read(address);
    let result = worker(self, value);
    self.write(address, result);
}

/// INC's worker: one more, clock rules.
fn inc_value(&mut self, value: u8) -> u8 {
    let result = value.wrapping_add(1);
    self.update_zero_and_negative(result);
    result
}

/// DEC's worker: one less, clock rules — 0 rolls back to 255.
fn dec_value(&mut self, value: u8) -> u8 {
    let result = value.wrapping_sub(1);
    self.update_zero_and_negative(result);
    result
}

Read modify’s signature slowly: its second parameter is a function. In Rust, a plain function’s name is a value — you can hand it to another function like you’d hand it a number. So modify owns the fetch-and-put-back plumbing forever, and each instruction just contributes its little worker. Watch how cheap the arms become — after the transfers:

Bit tricks

Chapter 3’s bit tools, promoted to instructions: AND keeps shared bits, ORA switches bits on, EOR flips (that’s ^ — chapter 7’s footnote, now a citizen). Games use these constantly: masking a sprite’s attributes, setting one option bit, toggling a state. Four workers, after dec_value:

    self.update_zero_and_negative(result);
    result

/// AND — keep only the bits A and the value share.
fn and(&mut self, mode: AddressingMode) {
    let address = self.operand_address(mode);
    let value = self.read(address);
    self.a &= value;
    self.update_zero_and_negative(self.a);
}

/// ORA — switch on every bit the value has on.
fn ora(&mut self, mode: AddressingMode) {
    let address = self.operand_address(mode);
    let value = self.read(address);
    self.a |= value;
    self.update_zero_and_negative(self.a);
}

/// EOR — exclusive or: flip every bit the value has on.
fn eor(&mut self, mode: AddressingMode) {
    let address = self.operand_address(mode);
    let value = self.read(address);
    self.a ^= value;
    self.update_zero_and_negative(self.a);
}

/// BIT — test BITs without touching A. Zero reports whether A and
/// the value share any set bits; N and V become plain copies of the
/// value's top two bits — which is why the flag masks fit.
fn bit(&mut self, mode: AddressingMode) {
    let address = self.operand_address(mode);
    let value = self.read(address);

    if self.a & value == 0 {
        self.status |= FLAG_ZERO;
    } else {
        self.status &= !FLAG_ZERO;
    }
    if value & FLAG_NEGATIVE != 0 {
        self.status |= FLAG_NEGATIVE;
    } else {
        self.status &= !FLAG_NEGATIVE;
    }
    if value & FLAG_OVERFLOW != 0 {
        self.status |= FLAG_OVERFLOW;
    } else {
        self.status &= !FLAG_OVERFLOW;
    }
}

The odd one out is BIT: it tests bits without touching A — and it copies the value’s top two bits straight into N and V, which is why our flag masks slot in as if they were made for it (they were). Keep an eye on BIT: in chapter 15, asking a certain chip “are you in vblank?” will be exactly this instruction reading exactly that top bit.

Sliding bits

The shifts: every bit moves one slot left or right. ASL doubles (the top bit falls into Carry — the ninth-bit story again); LSR halves (the bottom bit falls into Carry). ROL and ROR are their circular cousins: the old Carry comes back in the far end, making a nine-bit circle — the trick behind multi-byte shifts. Four workers, after bit:

src/cpu.rs

        self.status &= !FLAG_OVERFLOW;
    }
}

/// ASL's worker — Arithmetic Shift Left: every bit one slot up,
/// a 0 in at the bottom, the old top bit out into Carry.
/// Numerically: times two, ninth bit caught.
fn asl_value(&mut self, value: u8) -> u8 {
    if value & 0x80 != 0 {
        self.status |= FLAG_CARRY;
    } else {
        self.status &= !FLAG_CARRY;
    }
    let result = value << 1;
    self.update_zero_and_negative(result);
    result
}

/// LSR's worker — Logical Shift Right: divide by two, the old
/// bottom bit out into Carry.
fn lsr_value(&mut self, value: u8) -> u8 {
    if value & 0x01 != 0 {
        self.status |= FLAG_CARRY;
    } else {
        self.status &= !FLAG_CARRY;
    }
    let result = value >> 1;
    self.update_zero_and_negative(result);
    result
}

/// ROL's worker — ROtate Left: like ASL, but the OLD Carry comes
/// in at the bottom. Nine bits going around in a circle.
fn rol_value(&mut self, value: u8) -> u8 {
    let old_carry = self.status & FLAG_CARRY != 0;
    if value & 0x80 != 0 {
        self.status |= FLAG_CARRY;
    } else {
        self.status &= !FLAG_CARRY;
    }
    let mut result = value << 1;
    if old_carry {
        result |= 0x01;
    }
    self.update_zero_and_negative(result);
    result
}

/// ROR's worker — the same circle, turning the other way.
fn ror_value(&mut self, value: u8) -> u8 {
    let old_carry = self.status & FLAG_CARRY != 0;
    if value & 0x01 != 0 {
        self.status |= FLAG_CARRY;
    } else {
        self.status &= !FLAG_CARRY;
    }
    let mut result = value >> 1;
    if old_carry {
        result |= 0x80;
    }
    self.update_zero_and_negative(result);
    result
}

/// zero — a signed-arithmetic accident the Carry can't see.
pub const FLAG_OVERFLOW: u8 = 0b0100_0000;

/// The Interrupt-disable flag: the CPU's "do not disturb" sign.
pub const FLAG_INTERRUPT_DISABLE: u8 = 0b0000_0100;

/// The Decimal flag. On most 6502s it switches ADC and SBC into
/// base-ten mode. The NES's chip lets you set it — and ignores it.
/// The flag flips; the math never changes. We are exactly that honest.
pub const FLAG_DECIMAL: u8 = 0b0000_1000;

/// The ways an instruction can say WHERE its value lives.
/// (`Clone, Copy` lets us hand modes around as freely as numbers.)

Read the Decimal comment twice; it’s not a joke. The NES’s CPU is a 6502 with the base-ten circuitry disconnected — the flag flips, the math never changes. Our emulator gets this right by doing nothing, which is the best kind of accurate.

TXS is a famous little trap: it’s the only transfer that sets no flags. SP is plumbing, not data, and the chip treats it so. Emulators that miss this fail chapter 12’s exam on line one-hundred-something — ask me how everyone knows.

The jump with a hole in it

JMP has a second flavor we skipped in chapter 7: indirect — JMP ($0210) — follow a full 16-bit pointer. It’s how games jump to an address they computed at runtime.

It also carries the most famous bug in the chip. If the pointer sits at the very end of a page — JMP ($02FF) — the chip should read bytes from $02FF and $0300. It doesn’t. The second read wraps back to the start of the same page, $0200. A plain mistake in the silicon — but it was printed into millions of chips, games shipped that depend on it, and so the mistake stopped being a mistake and became the law. The worker implements the law, not the intention — after ror_value:

src/cpu.rs

    self.update_zero_and_negative(result);
    result
}

/// JMP's indirect flavor: follow a full 16-bit pointer — with the
/// 6502's famous flaw. If the pointer starts at the END of a page
/// ($xxFF), the chip fetches the second byte from the START of that
/// same page, not from the next one. A mistake printed into millions
/// of chips stops being a mistake: games rely on it, so it's the
/// law, and we obey the law.
fn jmp_indirect(&mut self) {
    let pointer = self.operand_address(AddressingMode::Absolute);

    let low = self.read(pointer) as u16;
    let high_address = if pointer & 0x00FF == 0x00FF {
        pointer & 0xFF00 // wrap to the page's own start
    } else {
        pointer + 1
    };
    let high = self.read(high_address) as u16;

    self.pc = (high << 8) | low;
}

/// Almost every instruction ends the same way: the CPU looks at the
/// value it just produced and updates two flags about it.

    #[test]
    fn txs_moves_x_to_sp_and_tsx_back() {
        // LDX #5, TXS, LDX #0, TSX — SP remembers, X gets it back.
        let cpu = run_program(&[0xA2, 0x05, 0x9A, 0xA2, 0x00, 0xBA, 0x00]);
        assert_eq!(cpu.x, 5);
    }

    #[test]
    fn sei_sed_set_their_flags_and_clv_clears_overflow() {
        // SEI, SED — then stage an overflow and CLV it away.
        let cpu = run_program(&[0x78, 0xF8, 0xA9, 0x50, 0x69, 0x50, 0xB8, 0x00]);
        assert!(cpu.status & FLAG_INTERRUPT_DISABLE != 0);
        assert!(cpu.status & FLAG_DECIMAL != 0);
        assert!(cpu.status & FLAG_OVERFLOW == 0);
    }

    #[test]
    fn jmp_indirect_follows_the_pointer() {
        // The pointer at $0210 says $8005, where BRK waits; the LDA
        // at $8003 gets jumped over.
        let cpu = run_program_with(
            &[0x6C, 0x10, 0x02, 0xA9, 0x63, 0x00],
            &[(0x0210, 0x05), (0x0211, 0x80)],
        );
        assert_eq!(cpu.a, 0);
    }

    #[test]
    fn jmp_indirect_obeys_the_page_edge_law() {
        // Pointer at $02FF: low byte from $02FF, high byte from $0200 —
        // NOT $0300. A decoy program waits where a wrong answer leads.
        let cpu = run_program_with(
            &[0x6C, 0xFF, 0x02, 0xA9, 0x63, 0x00],
            &[
                (0x02FF, 0x05),
                (0x0200, 0x80),
                (0x0300, 0x99),   // wrong high byte would send us to $9905...
                (0x9905, 0xA9),   // ...where a decoy LDA #$42 tells on it.
                (0x9906, 0x42),
            ],
        );
        assert_eq!(cpu.a, 0);
    }
}

Two deserve a highlight. inc_and_dec_count_in_memory plants 41 in a cell and counts it to the answer. And jmp_indirect_obeys_the_page_edge_law plants a decoy program where the wrong high byte would land — if your emulator reads the “sensible” address instead of the lawful one, the decoy tattles. cargo test: fifty green, and every official opcode except two named debts is alive in your machine.

For the curious

Why does the map have empty cells at all? The 6502’s decoder isn’t a lookup table — it’s a grid of partial patterns, and the “empty” combinations still do things: half-finished mixtures of neighboring instructions. Some freeze the chip; some do stable, useful accidents that later programmers adopted (a load into two pockets at once, for instance). Emulating the popular ones is a real requirement for a serious NES emulator — a story Part II tells properly.
