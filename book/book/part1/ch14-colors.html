Build Your Own NES Emulator

Colors

The album is open; the art is gray. One short chapter fixes that — and on the way you’ll learn the NES’s whole theory of color, which is less like painting and more like being handed a crayon box with the lid glued half-shut.

A crayon box, not a paint mixer

A modern screen mixes color: any red, any green, any blue, sixteen million shades. The NES does no such thing. It owns exactly 64 colors, fixed in silicon at the factory, and every frame of every game ever made picks from those and nothing else:

The box has architecture. Each column is a hue; each row is that hue at one of four brightnesses — because a color, to the chip, literally is those two numbers: which phase of a TV signal to wobble (the hue) and how hard (the brightness). Column $x0 has no wobble at all: the grays. Columns $xE and $xF never rise off the floor — eight crayons, all black — and $0D and $1D join them, for ten blacks in a 64-crayon box. The box repeats itself elsewhere too: $20 and $30 are the same white, and $10 and $3D are all but the same gray. (On the real chip a few of these twins differ by a whisker — Part II’s finer palette recovers them.) Nobody said 1983 was fair.

The crayon box in code

Where do the RGB numbers for those 64 crayons come from? The true answer: the chip stores none. It emits an analog television signal, and turning that into RGB is an act of interpretation — every emulator’s palette is one reading of it, which is why screenshots of the same game from different emulators never quite match. The table you are about to type was computed from the signal’s documented voltages, and in Part II the emulator will do that computation itself (and discover the box is secretly even bigger). Four crayons at a time

What makes 2-bit pixels livable is a sleight of hand. A tile’s pixel values 0–3 don’t pick from the big box directly — they pick from a palette: a hand of four crayons chosen from the 64. Different palette, same tile, different picture. One set of letter tiles can be white on the title screen and red in the game-over screen, at the cost of four bytes.

The machine keeps eight such hands at once — four for backgrounds, four for sprites — in a little scrap of PPU memory that games fill at boot. That scrap arrives with the rest of the PPU’s memory in chapter 15; today, since nobody has told our machine any palettes yet, we’ll supply our own. In main.rs, under the HEIGHT constant:

/// Draw every tile in CHR ROM through a palette: each pixel value picks
/// a crayon, each crayon picks a color from the big box. Pattern table
/// 0 on the left, table 1 on the right.
fn draw_pattern_tables(chr: &[u8], palette: &[u8; 4], buffer: &mut [u32]) {
    for table in 0..2 {
        for tile in 0..256 {
            let pixels = ppu::decode_tile(chr, table * 256 + tile);

            // Sixteen tiles to a row; the second table starts 128
            // pixels to the right; 56 centers it all vertically.
            let corner_x = table * 128 + (tile % 16) * 8;
            let corner_y = 56 + (tile / 16) * 8;

            for row in 0..8 {
                for col in 0..8 {
                    let crayon = palette[pixels[row][col] as usize];
                    let color = ppu::SYSTEM_PALETTE[crayon as usize];
                    buffer[(corner_y + row) * WIDTH + corner_x + col] = color;
                }
            }
        }
    }
}

while window.is_open() && !window.is_key_down(Key::Escape) {
    // Space tries the next palette on the album.
    if window.is_key_pressed(Key::Space, KeyRepeat::No) {

    #[test]
    fn famous_crayons_are_where_they_belong() {
        // $0F is the NES's true black; $20 and $30 are its whites; the
        // $x0 column is the grays, darkest to lightest.
        assert_eq!(SYSTEM_PALETTE[0x0F], 0x000000);
        assert_eq!(SYSTEM_PALETTE[0x20], SYSTEM_PALETTE[0x30]);
        // The white, pinned to the exact byte: a rounding slip here
        // passes every other test and shows up only when a frame sits
        // next to a reference picture.
        assert_eq!(SYSTEM_PALETTE[0x20], 0xFEFEFE);
        assert!(SYSTEM_PALETTE[0x00] < SYSTEM_PALETTE[0x10]);
    }

    #[test]
    fn every_crayon_is_plain_rgb() {
        // No alpha surprises for the frame buffer.
        for color in SYSTEM_PALETTE {
            assert_eq!(color >> 24, 0);
        }
    }
}

Honest admission: a table of constants is hard to test deeply — these pin the landmarks (the true black at $0F, the twin whites, the gray ladder rising) so a future finger-slip in the table has tripwires to hit. The real test of these 64 numbers is the one you just ran with your eyes. cargo test: sixty-four green.

Try it

  • Build a palette of the four blacks — [0x0D, 0x0E, 0x0F, 0x1D] — and enjoy the world’s least useful sticker album.
  • Make crayon 0 loud again: change each sample’s first entry to $24 (hot pink) and see chapter 13’s transparency exercise in full color.
  • Sort out a “night mode”: take the embers palette and drop every crayon one brightness row (subtract $10). That’s genuinely how games do dusk.

For the curious

Crayon $0D is infamous. It sits below the signal’s official black level — “blacker than black” — in territory a television reserves for sync signals, and on some sets using it makes the picture tear or roll. Licensed games avoided it; our table just renders it black and no monitors are harmed. The forbidden crayon is a good early taste of a Part II theme: the NES’s outputs were signals for imperfect machines, and emulating the numbers is not always the same as emulating the truth.
