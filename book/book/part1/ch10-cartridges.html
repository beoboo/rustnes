Build Your Own NES Emulator

Cartridges

Every program our CPU has run so far, we assembled by hand and poked into memory ourselves. Meanwhile, out in the world, there are thousands of real NES programs — games — sitting in .nes files. Today your emulator opens one, looks inside, and tells you what it found. First contact.

What’s inside the plastic

A NES cartridge is not a storage device the way a disk is. It’s circuitry — when one clicks into the console, its chips join the machine’s wiring directly. The console without a cartridge isn’t a computer missing a file; it’s a computer missing part of its board.

Two chips matter to us. PRG ROM — the PRoGram — holds code and data for the CPU; it’s what fills the top half of the address space, and it’s why the reset vector lives way up at $FFFC: that address is on the cartridge, where every game writes its own starting note. CHR ROM — the CHaRacters — holds tile graphics, and it isn’t wired to the CPU at all: it belongs to the picture chip, wired into a separate address space we’ll meet in chapter 13.

Bigger games add more chips — extra banks, batteries, even little co-processors — and those boards come in named varieties. For now, one fact and one number: the board type is called the mapper, and the simplest one, plain NROM with no tricks, is mapper 0. Chapters 28 and 29 climb the fancier ones.

A file wearing a header

A .nes file is the contents of those two ROM chips, with sixteen bytes of description stapled on front:

My favorite thing about this format: it has nothing to do with Nintendo. No cartridge contains a header — chips don’t need descriptions of themselves. The format was invented in 1996 for an emulator called iNES, by Marat Fayzullin, and the community simply adopted it. The magic bytes spell the emulator’s name, not the console’s. Thirty years later, every NES emulator ever written — including yours, as of today — speaks a fan-made format older than some of its authors.

Reading it

New machine part, new drawer. Create src/cartridge.rs, starting with the struct:

src/cartridge.rs

//! The cartridge — the game itself.

/// What comes out of a .nes file: the two ROMs and the board type.
pub struct Cartridge {
    /// PRG ROM — the PRoGram: code and data for the CPU.
    pub prg_rom: Vec<u8>,

    /// CHR ROM — the CHaRacters: tile graphics for the picture chip.
    pub chr_rom: Vec<u8>,

    /// Which cartridge board ("mapper") the game expects. Number 0 is
    /// NROM, the simplest: two ROMs, no tricks.
    pub mapper: u8,
}

Vec<u8> is a growable list of bytes that owns its contents — the right home for ROMs whose size we won’t know until we read the header. Announce the drawer in main.rs, under mod cpu;:

Now the parser. One new Rust idea in its signature: it returns Result — either a cartridge or an error message. Files come from the outside world, and the outside world contains cats walking on keyboards; a parser that can say “no, and here’s why” beats one that can only crash. (You’ve already handled Results — .expect() on Window::new was exactly this, choosing to crash politely.)

impl Cartridge {
    /// Unpack an iNES file: sixteen bytes of header, then the ROMs.
    pub fn load(bytes: &[u8]) -> Result<Cartridge, String> {
        // Every iNES file opens with the same four bytes: the letters
        // N, E, S, then $1A. Anything else is not our format.
        if bytes.len() < 16 || &bytes[0..4] != b"NES\x1A" {
            return Err("not an iNES file".to_string());
        }

        // The sizes come in chunks: PRG in 16 KiB units, CHR in 8 KiB.
        let prg_size = bytes[4] as usize * 16 * 1024;
        let chr_size = bytes[5] as usize * 8 * 1024;

        // The mapper number arrives split in half: its low four bits
        // ride in the top of byte 6, its high four bits in byte 7.
        let mapper = (bytes[7] & 0xF0) | (bytes[6] >> 4);

        // Some old files carry a 512-byte "trainer" before the ROMs —
        // a relic of 1990s copying hardware. Step politely over it.
        let mut start = 16;
        if bytes[6] & 0b0000_0100 != 0 {
            start += 512;
        }

        if bytes.len() < start + prg_size + chr_size {
            return Err("file is shorter than its header promises".to_string());
        }

        Ok(Cartridge {
            prg_rom: bytes[start..start + prg_size].to_vec(),
            chr_rom: bytes[start + prg_size..start + prg_size + chr_size].to_vec(),
            mapper,
        })
    }
}

Parsing is just careful reading: check the magic bytes, take the sizes, reassemble the mapper number from its two halves, step over the antique trainer field if flagged, and slice out the two ROMs. to_vec copies each slice into the cartridge’s own storage. (Byte 6 holds one more secret we step over today — a single bit describing how the board is wired — and chapter 15 will come back for it with a story.)

The simplest cartridge

One ability and the cartridge is useful: let the CPU-side world read PRG ROM the way the console wires it — as addresses $8000 through $FFFF. There’s a wrinkle, and it’s a lovely one. That window is 32 KiB, but plenty of games — including some famous ones — shipped only 16. What fills the other half? The same 16 KiB, again. Add read_prg inside the impl, after load:

src/cartridge.rs

    /// Read from PRG ROM as the CPU will see it: addresses $8000-$FFFF.
    /// A 32 KiB program fills that window exactly. A 16 KiB program
    /// appears TWICE — the smaller board simply doesn't connect the
    /// address wire that could tell the two halves apart, and the
    /// modulo plays the part of the missing wire.
    pub fn read_prg(&self, address: u16) -> u8 {
        let offset = (address as usize - 0x8000) % self.prg_rom.len();
        self.prg_rom[offset]
    }
}

This is our second bug-that-is-law, cousin to chapter 9’s jump: reading $C000 on a small NROM board genuinely returns the $8000 bytes, games genuinely put their reset vectors up there knowing it, and one % reproduces the arrangement. Cheap hardware, faithfully emulated, is still cheap hardware.

/// Load a .nes file and report what's inside the plastic.
fn rom_info(path: &str) {
    let bytes = std::fs::read(path).expect("could not read the file");
    let cartridge = Cartridge::load(&bytes).expect("could not parse the file");

    println!();
    println!("  {path}");
    println!("  PRG ROM: {} KiB (the program)", cartridge.prg_rom.len() / 1024);
    println!("  CHR ROM: {} KiB (the graphics)", cartridge.chr_rom.len() / 1024);
    println!("  mapper:  {}", cartridge.mapper);

    // The reset vector, straight off the cartridge: where this game's
    // program begins.
    let low = cartridge.read_prg(0xFFFC) as u16;
    let high = cartridge.read_prg(0xFFFD) as u16;
    println!("  starts at: ${:04X}", (high << 8) | low);
}

Small printout, big moment: those are the vital signs of a real game, read by your code — and that starts at address is Chase’s actual reset vector, the first place its author’s program counter ever pointed. Look at it again, though. $C000 — on a 16 KiB board. That address only exists because of the echo you built ten minutes ago: the game starts inside the mirror, on purpose, exactly as its author intended. The CPU that will follow it there is sitting one file over. Chapter 11 introduces them.

#[cfg(test)]
mod tests {
    use super::*;

    /// Build a tiny iNES file in memory: a header plus filler ROMs.
    fn fake_rom(prg_banks: u8, chr_banks: u8) -> Vec<u8> {
        let mut bytes = vec![0u8; 16];
        bytes[0..4].copy_from_slice(b"NES\x1A");
        bytes[4] = prg_banks;
        bytes[5] = chr_banks;
        bytes.extend(vec![0xAB; prg_banks as usize * 16 * 1024]);
        bytes.extend(vec![0xCD; chr_banks as usize * 8 * 1024]);
        bytes
    }

    #[test]
    fn load_reads_the_header() {
        let cartridge = Cartridge::load(&fake_rom(2, 1)).unwrap();
        assert_eq!(cartridge.prg_rom.len(), 32 * 1024);
        assert_eq!(cartridge.chr_rom.len(), 8 * 1024);
        assert_eq!(cartridge.mapper, 0);
    }

    #[test]
    fn a_wrong_magic_number_is_refused() {
        let mut bytes = fake_rom(1, 1);
        bytes[0] = b'X';
        assert!(Cartridge::load(&bytes).is_err());
    }

    #[test]
    fn a_16k_program_appears_twice() {
        // One PRG bank: $8000 and $C000 read the same byte.
        let mut bytes = fake_rom(1, 1);
        bytes[16] = 0x42; // the first PRG byte
        let cartridge = Cartridge::load(&bytes).unwrap();
        assert_eq!(cartridge.read_prg(0x8000), 0x42);
        assert_eq!(cartridge.read_prg(0xC000), 0x42);
    }

    #[test]
    fn a_32k_program_fills_the_window() {
        let mut bytes = fake_rom(2, 1);
        bytes[16] = 0x11; // first byte of the first bank
        bytes[16 + 16 * 1024] = 0x22; // first byte of the second bank
        let cartridge = Cartridge::load(&bytes).unwrap();
        assert_eq!(cartridge.read_prg(0x8000), 0x11);
        assert_eq!(cartridge.read_prg(0xC000), 0x22);
    }

    #[test]
    fn the_mapper_number_reassembles_from_its_halves() {
        let mut bytes = fake_rom(1, 1);
        bytes[6] = 0x40; // low half 4, riding in the top of byte 6
        bytes[7] = 0x20; // high half 2
        let cartridge = Cartridge::load(&bytes).unwrap();
        assert_eq!(cartridge.mapper, 0x24);
    }
}

Try it

  • Point rom_info at something that isn’t a ROM — a photo, this chapter’s HTML file. Enjoy the polite refusal.
  • Feed it a real ROM with a nonzero mapper, if you have one. The report works fine — we can describe any cartridge; we just can’t run the fancy ones yet.
  • Add a test: a file whose header promises more ROM than the file contains must be refused.

For the curious

Why is CHR ROM often so small — 8 KiB against a 32 KiB program? Because tiles are astonishingly compact: chapter 13 will show you that a whole 8×8 tile costs just 16 bytes, so 8 KiB holds 512 of them — every hero, letter, and cloud a game needs, if the artists are clever about reuse. The program is usually the expensive part.
