Build Your Own NES Emulator

Welcome

You are going to build a NES emulator: a program that pretends to be the little gray games console from the 1980s — and pretends so well that real games can’t tell the difference. They’ll run. On code you typed.

You’ll build it in Rust, by hand, every line explained: first a CPU that can count to twelve (a proud day), then pictures, then a whole game world with sound and a controller. The controller is your keyboard. We’ll cope.

By the end of Part I your emulator plays a real game, start to finish. After that, if you’re brave, Parts II and III go after the harder question — not “does it run?” but “is it right?” — which is where emulator building turns into detective work.

Hello, pixels

Every hero, every castle, every GAME OVER a NES ever showed was a grid of little colored dots: 256 across, 240 down. That’s 61,440 pixels, and by the end of this chapter, every single one of them works for you.

Borrowing a window

Opening a window works differently on Windows, on macOS, and on Linux, and all three ways are boring. So we won’t do it. Rust programmers share code in packages called crates, and somebody already wrote the one we want: minifb, “mini frame buffer”. It opens a window and shows pixels in it. No menus, no buttons, no opinions.

Tell Cargo we want it — add this at the bottom of Cargo.toml:

Cargo.toml

[dependencies]
# minifb ("mini frame buffer") opens a window and shows our pixels in it.
minifb = "0.27"

That’s a dependency: “my program needs that crate”. On the next build, Cargo downloads and compiles it without being asked twice.

A window full of nothing

Now the big idea — possibly of the whole book:

A picture is a list of numbers.

256 × 240 = 61,440 pixels. Make a list of 61,440 numbers, one per pixel, saying each one’s color — that list is the picture. It’s called a frame buffer, and you’re about to own one.

Delete everything in src/main.rs. At the top, the pieces of minifb we’ll use:

src/main.rs

use minifb::{Key, Scale, Window, WindowOptions};

Then names for our screen size, so 256 and 240 don’t wander the code as mystery numbers:

src/main.rs

const WIDTH: usize = 256;

/// ...and 240 pixels tall.
const HEIGHT: usize = 240;

And main itself: build the buffer, open a window, show the buffer until someone closes it:

src/main.rs

const HEIGHT: usize = 240;


fn main() {
    // The frame buffer: one number for every pixel on our screen.
    // 0 means black, so right now this is a picture of nothing.
    let mut buffer = vec![0u32; WIDTH * HEIGHT];

    // Ask the operating system for a window. `Scale::X2` doubles every pixel,
    // because 256x240 is tiny on a modern screen.
    let mut window = Window::new(
        "graybox",
        WIDTH,
        HEIGHT,
        WindowOptions {
            scale: Scale::X2,
            ..WindowOptions::default()
        },
    )
    .expect("could not open a window");

    // A real NES shows 60 pictures every second. So will we.
    window.set_target_fps(60);

    // Show the buffer, over and over, until the window is closed
    // or Esc is pressed.
    while window.is_open() && !window.is_key_down(Key::Escape) {
        window
            .update_with_buffer(&buffer, WIDTH, HEIGHT)
            .expect("could not draw to the window");
    }
}

Painting with numbers

So which number is which color?

Screen colors mix red, green, and blue light, each from 0 (off) to 255 (full blast). All three at 255: white. All zero: the black you’re admiring. One pixel’s number holds all three at once, packed side by side — in hexadecimal, 0xRRGGBB. So 0xFF0000 is pure red, 0x00FF00 pure green. (Hex feeling wobbly? Chapter 3 is a ten-minute detour built for exactly this moment.)

Let’s give all 61,440 pixels a different color, so there’s no doubt about who’s in charge now. Bottom of main.rs:

/// Fill the whole buffer with a smooth color gradient, so we can SEE that
/// every pixel is under our control.
fn draw_test_pattern(buffer: &mut [u32]) {
    for y in 0..HEIGHT {
        for x in 0..WIDTH {
            // Red grows from left to right. x already counts 0..=255,
            // which is exactly the range a color part can hold.
            let red = x as u32;

            // Green grows from top to bottom, stretched to reach 255
            // on the last row.
            let green = (y as u32 * 255) / (HEIGHT as u32 - 1);

            // A fixed dash of blue everywhere.
            let blue = 128;

            // Pack the three parts into one number: 0x00RRGGBB.
            let color = (red << 16) | (green << 8) | blue;

            buffer[y * WIDTH + x] = color;
        }
    }
}

<< slides each value into its slot of the packed number; | glues the slots together. Now call it — one line, right after the buffer is made:

And bottom-right, where red and green both hit full blast, comes out yellow. Notice there’s no pure red anywhere — the blue sneaks into every single mix. Every one of those 61,440 dots got its color from three lines of your arithmetic. (And the warning is gone — told you it just needed a minute.)

/// Darken every 8th row and column. The NES builds its whole picture out
/// of 8x8 tiles; this grid marks their territory.
fn draw_tile_grid(buffer: &mut [u32]) {
    for y in 0..HEIGHT {
        for x in 0..WIDTH {
            if x % 8 == 0 || y % 8 == 0 {
                let color = buffer[y * WIDTH + x];

                // pixel. The mask clears the bits that spilled over from

A brain with small pockets

The window is your emulator’s face. Time to grow a brain.

The NES’s CPU is (very nearly) a famous chip called the 6502 — the same one inside the Apple II and the Commodore 64. It’s almost fifty years old, it has three usable pockets, and it conquered the world anyway. Best of all, it’s small enough to fit entirely inside your head. By the end of the next chapter, yours runs its first program. This chapter builds the body: nouns today, verbs tomorrow.

What a CPU actually does

Here is the entire secret of every computer ever built. A CPU does one thing, forever:

  1. Read the next instruction from memory.
  2. Do what it says.
  3. Repeat.

That’s the whole trick. An instruction is tiny — “add these”, “copy that”, “jump there” — and the CPU never sees the big picture. It doesn’t know it’s running a game. It doesn’t know what a game is. It follows its recipe one step at a time, millions of steps per second, and castles and heroes emerge. Which makes our job wonderfully dumb: imitate the little steps perfectly, and the castles come along for free.

The pockets

For those steps, the CPU keeps a few values closer than memory — in its own pockets, called registers. There are only six:

  • A, the accumulator: where arithmetic happens. Sums accumulate here. Naming was simpler in the seventies.
  • X and Y, the index registers: helper pockets, great at counting and at pointing into lists.
  • PC, the program counter: the address of the next instruction — the CPU’s finger on the recipe. Addresses are 16 bits, so it’s the one big pocket.
  • SP, the stack pointer: runs a clever gadget we build in chapter 8. Until then it rides along quietly.
  • P, the status register: eight yes/no flags in one byte — sticky notes the CPU writes to itself (“that was zero”, “that overflowed”). They wake up next chapter.

Past the pockets lies memory: 65,536 addresses, $0000 to $FFFF, one byte each. For now, our CPU will own all of it. That’s a simplification — the real machine shares memory between chips, and chapter 11 rewires ours honestly. The book always tells you when we cheat, and when we pay it back.

A new file for the brain

The CPU gets its own file. In Rust, every file in src/ is a module — a labeled drawer of related code. Announce the new drawer at the very top of main.rs, above the use line — declaring what the program is comes before importing what it borrows:

src/cpu.rs

//! The 6502 CPU — the brain of the NES.

/// The CPU: a handful of small "pockets" (registers) and the memory it
/// reads and writes.
pub struct Cpu {
    /// A, the accumulator: the pocket where answers happen.
    pub a: u8,

    /// X, an index register: a helper pocket, good at counting.
    pub x: u8,

    /// Y, the other index register.
    pub y: u8,

    /// The program counter: the ADDRESS of the next instruction.
    /// The only 16-bit pocket, because addresses are 16 bits.
    pub pc: u16,

    /// The stack pointer — where in page one the next push lands.
    pub sp: u8,

    /// The status byte: eight tiny yes/no flags packed into one byte.
    pub status: u8,

    /// 64 KiB of memory — every address from $0000 to $FFFF.
    pub memory: [u8; 65536],
}

Check the types against the figure: small pockets are u8 (one byte, 0–255), pc is u16 (it holds an address), and memory is an array — 65,536 bytes standing in a row.

Building one

A struct is only a blueprint. To stamp out an actual CPU, we write a constructor — by Rust custom, a function named new:

            y: 0,

impl Cpu means “things a Cpu can do” — and this one block will collect every ability the CPU ever learns, from reading memory today to running whole games later. So far it can exist, pockets empty, memory blank. Everyone starts somewhere.

Reading and writing memory

/// Read the byte stored at an address.
pub fn read(&self, address: u16) -> u8 {
    self.memory[address as usize]
}

/// Store a byte at an address.
pub fn write(&mut self, address: u16, value: u8) {
    self.memory[address as usize] = value;
}

An address is just a position in the array, so reading is looking and writing is placing. The as usize converts the address into the type Rust demands for array positions. These five lines look too small to matter. They are the door everything in this book walks through.

Two bytes make an address

One byte counts to 255. Addresses go to 65,535. So an address needs two bytes — and here comes the 6502’s little quirk: it stores the little end first. The address $8000 lives in memory as 00, then 80. This is called little-endian, it trips up every emulator author exactly once, and we’re getting our once over with now, in one tidy function:

src/cpu.rs

pub fn write(&mut self, address: u16, value: u8) {
    self.memory[address as usize] = value;
}

/// Read a two-byte number. The 6502 stores the LITTLE end first:
/// the number $8000 sits in memory as the bytes $00, $80.
pub fn read_word(&self, address: u16) -> u16 {
    let low = self.read(address) as u16;
    let high = self.read(address.wrapping_add(1)) as u16;

    // Slide the big half 8 bits to the left, then glue the halves.
    (high << 8) | low
}

high << 8 slides the big half into the top of the 16-bit number, | glues the halves — the same trick you used to pack colors in chapter 2.

Waking up

One puzzle left. At power-on, PC must point at the program’s first instruction. But every game starts somewhere different — how can the CPU possibly know where?

It reads a note. By agreement, the two bytes at $FFFC and $FFFD always hold the program’s starting address. Whoever makes the program (soon: the cartridge) leaves that note, and the CPU’s first act on waking is to read it and go there. The note is called the reset vector — and what a lovely design: the chip asks the game where to start.

src/cpu.rs

    /// Press the reset button.
    pub fn reset(&mut self) {
        self.a = 0;
        self.x = 0;
        self.y = 0;

        // The 6502's documented wake-up values, exactly as the real
        // chip's reset sequence leaves them.
        self.sp = 0xFD;
        self.status = 0b0010_0100;

        // The reset vector: the address stored AT $FFFC tells the CPU
        // where its program begins. The CPU's first act is to read it.
        self.pc = self.read_word(0xFFFC);
    }
}

Those two mystery values for sp and status are the 6502’s real wake-up state; their reasons live in chapters 8 and 17. Copy them on faith — the book keeps a list of its promises, and it keeps every one.

Fetch, decode, execute

The CPU from chapter 4 has pockets, memory, and a wake-up routine — and absolutely no idea what to do next. Today it learns. By the last page it runs a real machine-code program while you watch, register by register.

Instructions are just numbers

Chapter 2’s big idea was a picture is a list of numbers. Meet its twin:

A program is a list of numbers.

Every instruction the 6502 understands has a number, its opcode. 0xA9 means “load a value into A”. 0xE8 means “add 1 to X”. A program is those numbers sitting in memory, one after another, right where PC points. No words, no symbols — just bytes the chip was built to recognize. This is machine code, the realest code there is.

The 6502 has 151 official opcodes. Deep breath: today we need four.

The heartbeat

The eternal loop — read the next instruction, do it, repeat — has a proper name: the fetch–decode–execute cycle. It’s the heartbeat of every CPU ever made. One beat:

  • Fetch: read the byte PC points at; move PC past it.
  • Decode: which instruction is this number?
  • Execute: do it.

Let’s build one beat as a function called step. To begin with, it recognizes exactly two situations: BRK, and everything else — loudly. It goes in the impl Cpu block, right after reset:

src/cpu.rs

    // where its program begins. The CPU's first act is to read it.
    self.pc = self.read_word(0xFFFC);
}

/// Run ONE instruction: fetch it, decode it, execute it.
/// Returns `false` when the program says stop, `true` otherwise.
pub fn step(&mut self) -> bool {
    // FETCH: read the next instruction's number (its "opcode")
    // and move the program counter past it.
    let opcode = self.read(self.pc);
    self.pc = self.pc.wrapping_add(1);

    // DECODE and EXECUTE: recognize the opcode, do what it says.
    match opcode {
        // BRK — simplified into a stop sign until interrupts arrive
        // (chapter 18). The real thing is more interesting.
        0x00 => return false,

        // An opcode we don't implement. Stopping loudly beats
        // carrying on wrongly.
        _ => panic!("I don't know opcode {opcode:#04X} yet!"),
    }

    true
}

Two new Rust friends. match compares a value against patterns and runs the matching arm — tailor-made for “which opcode is this?”; _ is the catch-all. And wrapping_add is clock addition: the way minutes roll from 59 back to 00, a pocket rolls from 255 back to 0. Real CPU pockets wrap around like that, so ours must too.

And admire the catch-all’s manners: panic! stops everything with a message. That’s a feature. The alternative is an emulator that shrugs at an unknown instruction, carries on wrongly, and shows you a garbled game an hour later with no clue why. Stopping loudly beats being wrong quietly — tattoo that somewhere, it’s the motto of this whole project.

The first real instruction

Now the star: LDA, “LoaD A”. This flavor (0xA9, written LDA #value) is two bytes: the opcode, then the value to load, sitting right there — immediately after. Hence its name: immediate. The CPU reads A9 and knows the next byte is cargo, not an instruction.

Add LDA’s arm at the top of the match, right under the DECODE comment:

src/cpu.rs

// DECODE and EXECUTE: recognize the opcode, do what it says.
match opcode {
    // LDA #value — LoaD A with the byte right after the opcode.
    0xA9 => {
        let value = self.read(self.pc);
        self.pc = self.pc.wrapping_add(1);
        self.a = value;
    }

Fetching the operand looks exactly like fetching the opcode — read at PC, move PC on. Not an accident: instructions and their cargo flow through the same door, one byte at a time. (Other flavors of LDA get their value from far stranger places. That’s chapter 6, and it’s quite a tour.)

Notes the CPU writes to itself

Time to switch on that status register. After nearly every instruction, the 6502 jots two quick notes about the value it just handled:

  • Was it zero? (The Z flag.)
  • Was its top bit set? (The N flag — N for negative. Why the top bit means that is a chapter 7 story. For now: top bit on, flag on.)

Why take notes? Because decisions — “if the counter hit zero, stop looping” — work by reading them. Flags are how one instruction whispers to the next. Games gossip like this constantly.

/// Load a little machine-code program, wake the CPU, run it to the end,
/// and print every pocket after every instruction.
fn cpu_demo() {
    // Our first program: six bytes.
    //
    // bytes    meaning
    // A9 0A    LDA #10    put the number 10 into A
    // AA       TAX        copy A into X
    // E8       INX        add 1 to X
    // E8       INX        add 1 to X
    // 00       BRK        stop
    let program = [0xA9, 0x0A, 0xAA, 0xE8, 0xE8, 0x00];

    let mut cpu = Cpu::new();

    // Copy the program into memory at $8000 — the neighborhood where
    // cartridge programs traditionally live.
    for (i, byte) in program.iter().enumerate() {
        cpu.write(0x8000 + i as u16, *byte);
    }

    // Write $8000 into the reset vector, little end first,
    // so the CPU wakes up inside our program.
    cpu.write(0xFFFC, 0x00);
    cpu.write(0xFFFD, 0x80);

    cpu.reset();

    // Run it, printing every pocket after every instruction.
    println!("  pc     a  x  y");
    println!("  ---------------");
    loop {
        let keep_going = cpu.step();
        println!("  {:04X}   {:02X} {:02X} {:02X}", cpu.pc, cpu.a, cpu.x, cpu.y);
        if !keep_going {
            println!("  (BRK: the program is done)");
            break;
        }
    }
}

Many ways to find a number

LDA #10 puts ten into A. Lovely — if the program already knows it wants ten. But games mostly want numbers that live somewhere: the hero’s health, the current score, which door is locked. Those sit in memory, at addresses, and instructions need ways of saying where to look.

The 6502 has eight ways, called addressing modes, and LDA speaks all of them. Today we build all eight — once, in one place — and by the end, a value will leave A, hide in memory, and come back on command.

One instruction, many flavors

“LDA”, it turns out, is not one opcode. Each flavor gets its own:

Our step function will do the same — but if we wrote the finding-code eight times inside LDA, we’d have to write it eight times again for STA, and for ADC in chapter 7, and on and on. The 6502 reuses these modes everywhere, so we will too: one function that answers one question — where?

/// Where does this instruction's value live? Every addressing mode
/// answers differently. This function does the finding, and moves PC
/// past whatever bytes the mode used up.
fn operand_address(&mut self, mode: AddressingMode) -> u16 {
    match mode {
        // The value's address IS where PC points. Note it, step past.
        AddressingMode::Immediate => {
            let address = self.pc;
            self.pc = self.pc.wrapping_add(1);
            address
        }
    }
}

Look at the Immediate arm closely — it’s slightly sneaky. The value sits right where PC points, so its address… is PC. We note the address, hop over the value, done. Even “the value is right here” is just an address.

The fast lane

The first 256 addresses — $0000 to $00FF — are called the zero page, and the 6502 treats them as its favorite shelf. Naming one takes a single byte instead of two, which makes the instruction shorter and, on real hardware, faster. 6502 programmers guard their zero page like treasure.

Follow the pointer

Now the strangest and most powerful flavor. Sometimes a program can’t say the address in advance, because the address itself is data — computed while the game runs, stored in memory like any other value. A stored address has a name: a pointer.

The parentheses say everything: don’t stop at $20 — follow what you find there. And here’s why that changes everything: the pointer is two bytes of ordinary, writable memory. The program can re-aim it while running — at this level’s map now, at the next level’s later — and the same LDA serves both without changing a single instruction. Every “current thing” a game has (current level, current song, current enemy list) is somewhere downstream of a pointer like this one.

For the curious

Why is zero page genuinely faster on the real chip? Because every byte of an instruction takes one clock tick to fetch. LDA $10 is two bytes; LDA $0010 written absolutely is three. Same address, one tick slower — and in a game drawing 60 pictures a second, ticks are money. Memory is sliced into 256-byte pages ($0000–$00FF is page zero, $0100–$01FF page one, and so on); crossing from one page to another mid-count has its own costs, which becomes a whole story in Part II.

Doing math and making choices

Our CPU can fetch, carry things around, and count on one finger. Today it learns to compute — add, subtract, compare — and then the big one: to choose. By the last page, your emulator runs its first loop, and a loop is the moment a program stops being a to-do list and starts being a machine.

Adding

The 6502 has exactly one addition instruction: ADC, “ADd with Carry” — we’ll get to the Carry part in a moment. It adds a value into A, and it comes in the same eight flavors as LDA, which means operand_address is about to pay for itself again.

First, a new flag. Add it above FLAG_ZERO, at the top of cpu.rs:

/// The Carry flag: the ninth bit of the last addition — and, for
/// subtraction and comparing, the "no borrow needed" signal.
pub const FLAG_CARRY: u8 = 0b0000_0001;

/// The Zero flag: switched on when the last value the CPU handled was zero.

Here’s why. Add 200 + 100 in a pocket that only holds 0 to 255: the true answer, 300, needs a ninth bit, and the pocket has eight. The 6502 doesn’t panic and doesn’t lie — it keeps the eight bits it can (300 wraps to 44) and drops the ninth bit into the Carry flag. Nothing is lost; the extra bit is just… carried. Exactly what you do on paper when a column overflows: write the 4, carry the 1.

Numbers below zero

Time to pay a debt from chapter 5: why does the top bit mean negative?

A pocket holds 256 different patterns. Nobody says they have to mean 0 to 255 — that’s just one way to read them. The 6502’s other way: patterns starting with 0 mean 0 to 127, and patterns starting with 1 mean -128 to -1. So $FF is 255 in one reading and -1 in the other. This scheme is called two’s complement1, and its magic is that the CPU doesn’t care which reading you meant. Adding works identically either way: 4 + $FF wraps to 3, and 4 + (-1) is 3. Same bits, same circuit, two stories. The top bit tells you which side of zero you’re on in the signed story — and that’s what the N flag has been copying all along.

One accident is possible, though. Add 80 + 80: the true answer 160 doesn’t fit in -128..127, so its bit pattern starts with a 1 — two positive numbers “added up to” a negative. The Carry can’t see this (nothing fell out of the ninth bit); it’s a purely signed-story accident, so it gets its own flag:

Subtraction in disguise

Now the payoff of all that theory. The 6502 has SBC, “SuBtract with Carry” — and internally, it isn’t a second math circuit. /// subtraction that throws the answer away and keeps only the
/// notes. Carry means "no borrow was needed" — in other words,
/// register >= value.
fn compare(&mut self, mode: AddressingMode, register: u8) {
    let address = self.operand_address(mode);
    let value = self.read(address);

    if register >= value {
        self.status |= FLAG_CARRY;
    } else {
        self.status &= !FLAG_CARRY;
    }

}

Choosing

JMP always jumps. The branch family jumps if — and this is where the flags cash out. BEQ: branch if the Zero note says “equal”. BNE: if not equal. BCS/BCC ride the Carry, BPL/BMI the sign, BVS/BVC the Overflow.

Branches don’t carry a full address. They carry a one-byte offset: “hop this far from here” — and it’s a signed byte, our new friend two’s complement, so backwards is just a negative hop. (Why so stingy? A branch is the most common instruction in any program; making it two bytes instead of three saves memory everywhere and, on the real chip, time. There’s a cost: a branch can only reach 127 forward or 128 back. Games learn to live inside that.)

For the curious

The overflow spell, unrolled: a ^ result has its top bit set when A and the answer disagree about sign; value ^ result likewise for the value. Overflow is exactly “the answer disagrees with BOTH inputs” — two numbers on one side of zero can’t honestly land on the other. The & 0x80 keeps only the sign bit of all that. Three xors, one and: cheaper than any if-chain, and precisely what the real chip’s silicon computes.

  1. Picture the 256 patterns on a wheel, like a clock face: 0, 1, 2, … 255, and then back to 0 — the same wrapping our pockets have had since chapter 5. Stand at 0 and step backwards: you land on 255. So 255 behaves exactly like -1, 254 like -2, and in general -n sits at position 256 - n. Nobody decreed that; the wheel’s shape forces it. The scheme is just an agreement to read the wheel’s top half (128–255) as -128 to -1.

    The flip-the-bits trick follows: flipping every bit of n gives 255 - n (try it: 0000_0011 flips to 1111_1100, and 3 + 252 = 255); adding one gives 256 - n, the wheel’s position for -n. That’s SBC’s whole disguise — and the name: the complement to two-to-the-eighth (256), two’s complement. Check it against the subtraction test: 4 - 9 printed $FB = 251 = 256 - 5. Five steps back from zero: there’s your -5. ↩

  2. ^ is xor, “exclusive or” — the fourth bit tool, joining <<, |, and &. It compares two values bit by bit and answers 1 wherever they disagree, 0 wherever they agree. So a ^ b lights up exactly the bits where a and b differ — handy for “did the sign bit change?”. And xor-ing against a 1 always flips: a 0 disagrees with it, a 1 agrees — which is why x ^ 0xFF, all ones, flips every bit of x. Chapter 3’s bit tools section has the full kit. ↩

Remembering where you were

Chapter 7’s loop runs in a circle it was born in: the jump targets are burned into the program. But real programs are built from helpers — draw a tile, play a note, add the score — each used from a dozen places. A helper needs to answer one question the CPU can’t yet: when I’m done… where was I?

Today the CPU gets a memory for exactly that. It’s called the stack, it’s the reason SP has been riding along since chapter 4, and it is sneakily one of the great inventions of computing.

A stack of plates

Picture a pile of plates. You can put a plate on top, and you can take the top plate off. That’s all — no sliding one out of the middle. Whatever went on last comes off first.

That discipline has a name — a stack — and it’s precisely the shape of the “where was I?” problem. Call a helper: put your return place on the pile. The helper calls another helper: another plate on top. Each return takes the top plate — and every one is, automatically, the right one. Nesting for free, to any depth. That’s the whole trick, and the rest of the chapter is just plumbing it.

Page one

The 6502 keeps its plate-pile in memory, in page one — addresses $0100 to $01FF, 256 bytes reserved by the chip’s design. SP, the stack pointer, holds the low byte of the next free slot. And one delightful quirk: the pile grows downward. The first push lands at $01FD and SP steps down to $FC; pull steps back up. Top of the pile = lowest address used. Upside-down plates, working perfectly.

/// Push one byte onto the stack. The stack lives in page one,
/// $0100-$01FF; SP points at the NEXT free slot; and the pile grows
/// DOWNWARD - push writes, then steps down.
fn push(&mut self, value: u8) {
    self.write(0x0100 + self.sp as u16, value);
    self.sp = self.sp.wrapping_sub(1);
}

/// Pull one byte back off the stack: step up, then read.
/// (Most of the world says "pop"; the 6502 says "pull".)
fn pull(&mut self) -> u8 {
    self.sp = self.sp.wrapping_add(1);
    self.read(0x0100 + self.sp as u16)
}

/// Push a two-byte value: big half first, so that in memory it lies
/// little end first - the way the 6502 likes its addresses.
fn push_word(&mut self, value: u16) {
    self.push((value >> 8) as u8);
    self.push(value as u8);
}

/// Pull a two-byte value pushed by `push_word`.
fn pull_word(&mut self) -> u16 {
    let low = self.pull() as u16;
    let high = self.pull() as u16;
    (high << 8) | low
}

And a chapter 4 promise comes due: why did reset set SP to $FD, not $FF? Because the real chip’s reset sequence is three pushes in disguise — it runs its power-on routine through the same circuitry that pushes, stepping SP from $00 down past $FF and $FE to $FD, without actually writing anything. // JSR — Jump to SubRoutine: leave a return note on the
// stack, then go. The 6502's quirk: the note is the address
// of JSR's own LAST byte — one short of the next
// instruction. RTS knows, and adds the 1 back.
0x20 => {
    let target = self.operand_address(AddressingMode::Absolute);
    self.push_word(self.pc.wrapping_sub(1));
    self.pc = target;
}

// RTS — ReTurn from Subroutine: read the note, add the
// missing 1, resume as if nothing happened.
0x60 => {
    let return_address = self.pull_word();
    self.pc = return_address.wrapping_add(1);
}

// TAX — Transfer A to X. A keeps its value; X gets a copy.
0xAA => {
    self.x = self.a;

One genuine oddity, worth reading twice: JSR does not push the address of the next instruction. It pushes the address of its own last byte — one short. RTS adds the missing 1 after pulling. Why? Because inside the real chip, JSR’s push happens while the instruction is still being fetched, before PC has moved past it. Two quirks that cancel out — as long as every emulator author implements both halves. Our test will pin the pushed bytes exactly, because chapter 12’s golden log certainly will.

Counting in memory

INC and DEC count directly in a memory cell — no pocket involved. They’re our first read-modify-write instructions: fetch the value, change it, put it back. And since a whole family of instructions ahead shares that exact shape, we’ll build the shape itself, once.

/// Read-modify-write: fetch a value from memory, hand it to a worker
/// function, store the worker's answer back where the value came
/// from. The worker is a PARAMETER — in Rust, a plain function's
/// name is a value you can pass around, like any other.
fn modify(&mut self, mode: AddressingMode, worker: fn(&mut Cpu, u8) -> u8) {
    let address = self.operand_address(mode);
    let value = self.read(address);
    let result = worker(self, value);
    self.write(address, result);
}

/// INC's worker: one more, clock rules.
fn inc_value(&mut self, value: u8) -> u8 {
    let result = value.wrapping_add(1);
    self.update_zero_and_negative(result);
    result
}

/// DEC's worker: one less, clock rules — 0 rolls back to 255.
fn dec_value(&mut self, value: u8) -> u8 {
    let result = value.wrapping_sub(1);
    self.update_zero_and_negative(result);
    result
}

    if value & FLAG_NEGATIVE != 0 {
        self.status |= FLAG_NEGATIVE;
    } else {

        self.status &= !FLAG_OVERFLOW;

}

Sliding bits

The shifts: every bit moves one slot left or right. ASL doubles (the top bit falls into Carry — the ninth-bit story again); LSR halves (the bottom bit falls into Carry). /// ASL's worker — Arithmetic Shift Left: every bit one slot up,
/// a 0 in at the bottom, the old top bit out into Carry.
/// Numerically: times two, ninth bit caught.
fn asl_value(&mut self, value: u8) -> u8 {
    if value & 0x80 != 0 {
        self.status |= FLAG_CARRY;
    } else {
        self.status &= !FLAG_CARRY;
    }
    let result = value << 1;
    self.update_zero_and_negative(result);
    result
}

/// LSR's worker — Logical Shift Right: divide by two, the old
/// bottom bit out into Carry.
fn lsr_value(&mut self, value: u8) -> u8 {
    if value & 0x01 != 0 {
        self.status |= FLAG_CARRY;
    } else {
        self.status &= !FLAG_CARRY;
    }
    let result = value >> 1;
    self.update_zero_and_negative(result);
    result
}

/// ROL's worker — ROtate Left: like ASL, but the OLD Carry comes
/// in at the bottom. Nine bits going around in a circle.
fn rol_value(&mut self, value: u8) -> u8 {
    let old_carry = self.status & FLAG_CARRY != 0;
    if value & 0x80 != 0 {
        self.status |= FLAG_CARRY;
    } else {
        self.status &= !FLAG_CARRY;
    }
    let mut result = value << 1;
    if old_carry {
        result |= 0x01;
    }
    self.update_zero_and_negative(result);
    result
}

/// ROR's worker — the same circle, turning the other way.
fn ror_value(&mut self, value: u8) -> u8 {
    let old_carry = self.status & FLAG_CARRY != 0;
    if value & 0x01 != 0 {
        self.status |= FLAG_CARRY;
    } else {
        self.status &= !FLAG_CARRY;
    }
    let mut result = value >> 1;
    if old_carry {
        result |= 0x80;
    }
    self.update_zero_and_negative(result);
    result
}

The jump with a hole in it

JMP has a second flavor we skipped in chapter 7: indirect — JMP ($0210) — follow a full 16-bit pointer. It’s how games jump to an address they computed at runtime.

It also carries the most famous bug in the chip. If the pointer sits at the very end of a page — JMP ($02FF) — the chip should read bytes from $02FF and $0300. It doesn’t. The second read wraps back to the start of the same page, $0200. A plain mistake in the silicon — but it was printed into millions of chips, games shipped that depend on it, and so the mistake stopped being a mistake and became the law. The worker implements the law, not the intention — after ror_value:

/// JMP's indirect flavor: follow a full 16-bit pointer — with the
/// 6502's famous flaw. If the pointer starts at the END of a page
/// ($xxFF), the chip fetches the second byte from the START of that
/// same page, not from the next one. A mistake printed into millions
/// of chips stops being a mistake: games rely on it, so it's the
/// law, and we obey the law.
fn jmp_indirect(&mut self) {
    let pointer = self.operand_address(AddressingMode::Absolute);

    let low = self.read(pointer) as u16;
    let high_address = if pointer & 0x00FF == 0x00FF {
        pointer & 0xFF00 // wrap to the page's own start
    } else {
        pointer + 1
    };
    let high = self.read(high_address) as u16;

    self.pc = (high << 8) | low;
}

Cartridges

Every program our CPU has run so far, we assembled by hand and poked into memory ourselves. Meanwhile, out in the world, there are thousands of real NES programs — games — sitting in .nes files. Today your emulator opens one, looks inside, and tells you what it found. First contact.

What’s inside the plastic

A NES cartridge is not a storage device the way a disk is. It’s circuitry — when one clicks into the console, its chips join the machine’s wiring directly. The console without a cartridge isn’t a computer missing a file; it’s a computer missing part of its board.

Two chips matter to us. PRG ROM — the PRoGram — holds code and data for the CPU; it’s what fills the top half of the address space, and it’s why the reset vector lives way up at $FFFC: that address is on the cartridge, where every game writes its own starting note. CHR ROM — the CHaRacters — holds tile graphics, and it isn’t wired to the CPU at all: it belongs to the picture chip, wired into a separate address space we’ll meet in chapter 13.

Bigger games add more chips — extra banks, batteries, even little co-processors — and those boards come in named varieties. For now, one fact and one number: the board type is called the mapper, and the simplest one, plain NROM with no tricks, is mapper 0. Chapters 28 and 29 climb the fancier ones.

A file wearing a header

A .nes file is the contents of those two ROM chips, with sixteen bytes of description stapled on front:

My favorite thing about this format: it has nothing to do with Nintendo. No cartridge contains a header — chips don’t need descriptions of themselves. The format was invented in 1996 for an emulator called iNES, by Marat Fayzullin, and the community simply adopted it. The magic bytes spell the emulator’s name, not the console’s. Thirty years later, every NES emulator ever written — including yours, as of today — speaks a fan-made format older than some of its authors.

impl Cartridge {
    /// Unpack an iNES file: sixteen bytes of header, then the ROMs.
    pub fn load(bytes: &[u8]) -> Result<Cartridge, String> {
        // Every iNES file opens with the same four bytes: the letters
        // N, E, S, then $1A. Anything else is not our format.
        if bytes.len() < 16 || &bytes[0..4] != b"NES\x1A" {
            return Err("not an iNES file".to_string());
        }

        // The sizes come in chunks: PRG in 16 KiB units, CHR in 8 KiB.
        let prg_size = bytes[4] as usize * 16 * 1024;
        let chr_size = bytes[5] as usize * 8 * 1024;

        // The mapper number arrives split in half: its low four bits
        // ride in the top of byte 6, its high four bits in byte 7.
        let mapper = (bytes[7] & 0xF0) | (bytes[6] >> 4);

        // Some old files carry a 512-byte "trainer" before the ROMs —
        // a relic of 1990s copying hardware. Step politely over it.
        let mut start = 16;
        if bytes[6] & 0b0000_0100 != 0 {
            start += 512;
        }

        if bytes.len() < start + prg_size + chr_size {
            return Err("file is shorter than its header promises".to_string());
        }

        Ok(Cartridge {
            prg_rom: bytes[start..start + prg_size].to_vec(),
            chr_rom: bytes[start + prg_size..start + prg_size + chr_size].to_vec(),
            mapper,
        })
    }
}

Parsing is just careful reading: check the magic bytes, take the sizes, reassemble the mapper number from its two halves, step over the antique trainer field if flagged, and slice out the two ROMs. to_vec copies each slice into the cartridge’s own storage. The bus

Since chapter 4, our CPU has owned all 64 KiB of memory — one big private array. That was a simplification, and today it ends. In the real console the CPU owns nothing: it puts an address on a shared set of wires, and whichever chip recognizes that address answers. The wires are called the bus, and building one is what finally lets a real cartridge — Chase, from last chapter — plug into your machine and run.

This is also the biggest rewiring the book will ever ask of you. Watch how little actually changes — and fair warning: mid-chapter, the project won’t compile for a few sections. That’s what refactoring across a whole program feels like; we’ll land on green.

One street, many houses

An address is like a street number: the CPU just shouts it; living at the address is somebody else’s job. And the residents are strange. The console’s entire RAM is 2 KiB — your gradient buffer from chapter 2 is a hundred times bigger — yet it answers at four different address ranges, because decoding address wires precisely costs hardware and Nintendo preferred cheap. The same corner-cutting that mirrored Chase’s 16 KiB ROM mirrors the RAM too: echoes, everywhere, on purpose.

    /// One address in, one byte out — from whichever chip lives there.
    /// (A `..=` pattern matches a whole range of values at once.)
    pub fn read(&self, address: u16) -> u8 {
        match address {
            // The console's RAM — and its three echoes. The board only
            // decodes enough address wires to tell 2 KiB apart, so the
            // same bytes answer again at $0800, $1000, and $1800.
            0x0000..=0x1FFF => self.ram[address as usize % 2048],

            // The cartridge's program ROM.
            0x8000..=0xFFFF => self.cartridge.read_prg(address),
            _ => 0,
        }

    pub fn write(&mut self, address: u16, value: u8) {
        match address {
            0x0000..=0x1FFF => self.ram[address as usize % 2048] = value,

            // Writes to ROM change nothing. The clue is in the name.
            0x8000..=0xFFFF => {}

            // Everywhere else: nobody listening yet.
            _ => {}
        }

/// Run nestest in automation mode and grade our CPU against a golden
/// log, line by line. The first difference is the truth.
fn nestest_diff(rom_path: &str, log_path: &str) {
    let bytes = std::fs::read(rom_path).expect("could not read the ROM");
    let cartridge = Cartridge::load(&bytes).expect("could not parse the ROM");
    let golden = std::fs::read_to_string(log_path).expect("could not read the log");

    let mut cpu = Cpu::new(cartridge);
    cpu.reset();
    // nestest's automation mode: start at $C000 instead of the vector,
    // and the tests run with no picture chip needed at all.
    cpu.pc = 0xC000;

    let mut matched = 0;
    for line in golden.lines() {
        // The fields both sides have: PC and the five pockets. (The log
        // also carries cycle counts — a Part II subject.)
        let ours = format!(
            "{:04X} A:{:02X} X:{:02X} Y:{:02X} P:{:02X} SP:{:02X}",
            cpu.pc, cpu.a, cpu.x, cpu.y, cpu.status, cpu.sp
        );
        let theirs = format!("{} {}", &line[0..4], &line[48..73]);

        if ours != theirs {
            println!("MISMATCH after {matched} matching lines.");
            println!("  golden: {theirs}");
            println!("  ours:   {ours}");
            println!("  the golden line in full:");
            println!("  {line}");
            return;
        }
        matched += 1;

        if Cpu::opcode_name_and_length(cpu.read(cpu.pc)).is_none() {
            println!(
                "{matched} lines matched — then {:#04X}, an opcode we",
                cpu.read(cpu.pc)
            );
            println!("don't implement. Unofficial. A Part II story.");
            return;
        }
        cpu.step();
    }

A second brain

The PPU is not a helper of the CPU. It’s a second computer on the board, with its own job — drawing, sixty times a second — and, remarkably, its own memory in its own address space:

When the CPU says “address $0000,” the bus hands it RAM. When the PPU says “address $0000,” a completely different set of wires hands it the cartridge’s CHR ROM. Same numbers, different world — which is why chapter 10 could claim, straight-faced, that CHR isn’t wired to the CPU at all. The two chips share nothing but a few doorbell registers (that’s the $2002 Chase keeps ringing) and the cartridge sitting between them.

This chapter needs only the bottom half of that map: the pattern tables, where tiles live.

Pictures from squares

The PPU cannot draw a pixel wherever it likes. Every picture it will ever make is assembled from tiles — 8×8 pixel squares — like a mosaic, or stickers on a grid. The background is tiles. The hero is tiles. The letters in “GAME OVER” are tiles. That faint grid you drew back in chapter 2 was this fact, foreshadowed: 32 tiles across, 30 down, and nothing on a NES screen ever happens outside that scheme.

It sounds like a limitation, and it is — but it’s the load-bearing kind. It’s why 8 KiB of CHR can hold a whole game’s art, and (in Part II) it’s why the PPU can keep up with the TV at all.

Two bits per pixel

So how does a tile store its 64 pixels? With shameless thrift: two bits per pixel — each pixel is just a number from 0 to 3. Sixteen bytes per tile, laid out in a scheme worth a picture:

A tile’s sixteen bytes are two bit-planes: the first eight bytes carry every pixel’s low bit (one byte per row, bit 7 leftmost), the second eight carry every pixel’s high bit. To read one pixel you visit both planes, pluck the same bit from each, and stack them. Why store it sideways like this instead of two clean bits together? Because the chip reads a whole row of low bits in one byte-fetch and a whole row of high bits in the next — the format is shaped like the hardware’s appetite, a Part II story with a chapter of its own.

And what does a pixel value of 2 look like? No idea — and neither does the tile. 0 to 3 aren’t colors; they’re crayon numbers, waiting for a palette to give them meaning. That’s chapter 14. Today we’ll use four grays and like it.

//! The picture chip — built here, piece by piece, starting with the
//! part every picture is made of: tiles.

/// Decode one tile: 16 bytes of CHR become 8x8 pixels of 0..=3.
///
/// A tile's first 8 bytes are plane 0 (every pixel's low bit, one byte
/// per row), its second 8 are plane 1 (the high bits). Bit 7 is the
/// leftmost pixel.
pub fn decode_tile(chr: &[u8], tile: usize) -> [[u8; 8]; 8] {
    let start = tile * 16;
    let mut pixels = [[0u8; 8]; 8];

    for row in 0..8 {
        let plane0 = chr[start + row];
        let plane1 = chr[start + row + 8];

        for col in 0..8 {
            let bit = 7 - col;
            let low = (plane0 >> bit) & 1;
            let high = (plane1 >> bit) & 1;
            pixels[row][col] = (high << 1) | low;
        }
    }
    pixels
}

Colors

The album is open; the art is gray. One short chapter fixes that — and on the way you’ll learn the NES’s whole theory of color, which is less like painting and more like being handed a crayon box with the lid glued half-shut.

A crayon box, not a paint mixer

A modern screen mixes color: any red, any green, any blue, sixteen million shades. The NES does no such thing. It owns exactly 64 colors, fixed in silicon at the factory, and every frame of every game ever made picks from those and nothing else:

The box has architecture. Each column is a hue; each row is that hue at one of four brightnesses — because a color, to the chip, literally is those two numbers: which phase of a TV signal to wobble (the hue) and how hard (the brightness). Column $x0 has no wobble at all: the grays. Columns $xE and $xF never rise off the floor — eight crayons, all black — and $0D and $1D join them, for ten blacks in a 64-crayon box. The box repeats itself elsewhere too: $20 and $30 are the same white, and $10 and $3D are all but the same gray. (On the real chip a few of these twins differ by a whisker — Part II’s finer palette recovers them.) Nobody said 1983 was fair.

The map of the screen

Two rooms, four doors

Here’s a subtlety we cannot skip — I know, because I tried. The PPU’s address space has four nametable slots — $2000, $2400, $2800, $2C00 — but the console contains RAM for two. The cartridge’s board wires the four doors onto the two rooms, and a bit in the iNES header (byte 6, bit 0) says which way: vertical mirroring pairs $2000 with $2800; horizontal pairs $2000 with $2400. Why two arrangements? Scrolling — a game scrolls smoothly along one axis by treating two rooms as one tall or one wide picture. Our games don’t scroll yet, but the wiring matters today, and the war story below is about exactly that.

    /// real 1 KiB rooms. Four names, two rooms: VERTICAL mirroring puts
    /// the rooms side by side ($2000/$2800 share, $2400/$2C00 share);
    /// HORIZONTAL stacks them ($2000/$2400 share, $2800/$2C00 share).
    fn mirror(&self, address: u16) -> usize {
        let index = address as usize & 0x0FFF; // within the 4 KiB window
        let name = index / 0x400; // which of the four names, 0..=3
        let room = if self.vertical_mirroring {
            name & 1
        } else {
            name / 2

        room * 0x400 + (index & 0x3FF)
    }

/// A write to PPUADDR ($2006): half of an address — big half on the
/// first knock, little half on the second.
pub fn write_address(&mut self, value: u8) {
    let address = self.address.get();
    if self.expecting_low.get() {
        self.address.set((address & 0xFF00) | value as u16);
    } else {
        self.address.set((address & 0x00FF) | ((value as u16) << 8));
    }
    self.expecting_low.set(!self.expecting_low.get());
}

/// A write to PPUDATA ($2007): one byte into PPU memory, wherever
/// the address points — which then walks forward on its own.
pub fn write_data(&mut self, value: u8) {
    let address = self.address.get() & 0x3FFF;
    match address {
        // Pattern tables are the cartridge's ROM: writes bounce off.
        0x0000..=0x1FFF => {}

        // The nametables' two rooms, found through the board's
        // mirroring arrangement.
        0x2000..=0x3EFF => self.vram[self.mirror(address)] = value,

        // The palettes' 32 bytes.
        _ => self.palette_ram[address as usize & 0x001F] = value,
    }

    self.step_address();
}

/// The auto-step every PPUDATA access ends with: +1 normally, +32 —
/// one screen-row down — when PPUCTRL asks for column order.
fn step_address(&self) {
    let step = if self.ctrl & 0b0000_0100 != 0 { 32 } else { 1 };
    self.address.set(self.address.get().wrapping_add(step));
}

/// A read of PPUSTATUS ($2002): reports vblank in the top bit — and
/// the act of looking clears the flag AND resets the address
/// register to expect a first knock. Reading, here, is touching —
/// which is why those two fields live in `Cell`s.
pub fn read_status(&self) -> u8 {
    let status = (self.vblank.get() as u8) << 7;
    self.vblank.set(false);
    self.expecting_low.set(false);
    status
}

This is why those fields wear Cells: in Rust, reading goes through &self — a shared, read-only reference — and a plain bool behind &self cannot change. The tap on the shoulder

There are two ways to know it’s vblank. Chase’s boot showed the first: stand at the door and knock — poll $2002 until the answer changes. But polling costs the whole frame standing there, so once a game is running it uses the second way: hang a do-come-wake-me sign — bit 7 of PPUCTRL — and go to sleep. Watch either of our games past its boot: it blacks its palettes, writes $80 to PPUCTRL, and settles into a three-instruction nap, waiting for a counter that only a visitor can increment. That visitor is the NMI — the Non-Maskable Interrupt — vblank arriving not as an answer but as a tap on the shoulder. No tap, no title. Controllers

The locked door

So how would a game notice a button? The CPU can do exactly one thing: read and write addresses. So the console gives buttons an address. Sixty times a second, Chase asks $2002 “is it vblank?” — and, the same way, it asks $4016 “what is the player pressing?”. Up on that title screen it has been asking all along. Our bus answers 0. Forever. The door is locked from the outside.

Eight buttons on one wire

The thing we’re about to build is the gray brick you may know from photos: a cross of four arrows for the left thumb, round A and B for the right, Select and Start in the middle. Eight buttons — exactly one byte’s worth, so you’d expect the game to read them all in one gulp. It can’t, and the cable is why: a wire for every button would make it thick, stiff and expensive, and 1983 said no. The pad got one data wire, a tiny chip, and a rule: the buttons answer one at a time, like names read off a list:

The write side is the strobe — from the flashing light of the same name: a quick pulse, over in an instant. While the game holds it high, the chip stares at the buttons; the moment the game drops it, whatever it saw freezes. Reads then walk the frozen list, first button to last, one bit each. So the full ritual a game performs at $4016 reads: write 1 (stare), write 0 (freeze), then read eight times. Why freeze at all? Fairness: the player can mash mid-frame, but the game’s eight reads all describe one single instant.

A snapshot, one bit at a time

The whole device fits in a page. New file, src/controller.rs:

src/controller.rs

//! The controller — eight buttons on one wire, read a bit at a time.

use std::cell::Cell;

/// One NES controller. All eight buttons fit in one byte, in the
/// order the console shifts them out: A, B, Select, Start, Up, Down,
/// Left, Right — A in bit 0, Right in bit 7.
pub struct Controller {
    /// What the player is holding at this instant. The window loop
    /// keeps this fresh; the game never sees it directly.
    pub buttons: u8,

    /// The frozen copy the game actually reads, taken the moment the
    /// strobe drops.
    snapshot: u8,

    /// The "stare at the buttons" line. High: the pad watches the
    /// buttons live. Dropped: the snapshot freezes.
    strobe: bool,

    /// Which bit of the snapshot the next read hands out. A `Cell`,
    /// for the same reason as the PPU's address: reading moves it.
    index: Cell<u8>,
}

impl Controller {
    pub fn new() -> Controller {
        Controller {
            buttons: 0,
            snapshot: 0,
            strobe: false,
            index: Cell::new(0),
        }
    }

    /// A write to $4016. Only bit 0 matters: raising it makes the pad
    /// stare at the buttons; dropping it freezes what it saw and
    /// rewinds to the first button.
    pub fn write(&mut self, value: u8) {
        let high = value & 1 != 0;
        if self.strobe && !high {
            self.snapshot = self.buttons;
            self.index.set(0);
        }
        self.strobe = high;
    }

    /// A read from $4016: the next button of the snapshot, low bit of
    /// the answer. While the strobe is high there IS no "next" —
    /// every read reports A, live. And past the eighth button a real
    /// pad answers 1, which is how games tell a controller from an
    /// empty port.
    pub fn read(&self) -> u8 {
        if self.strobe {
            return self.buttons & 1;
        }
        let index = self.index.get();
        if index < 8 {
            self.index.set(index + 1);
            (self.snapshot >> index) & 1
        } else {
            1
        }
    }
}

Sixty-four little forms

The PPU keeps its cast list in a memory of its own: OAM, Object Attribute Memory — 256 bytes, four per sprite. Four bytes is a whole character sheet:

The Y byte carries a famous quirk: the hardware draws every sprite one row lower than the byte says, so games store “top minus one” and nobody talks about it. It also gives games a free trick — write $EF or anything below it and the sprite starts past row 239: parked off the bottom of the world, invisible. An empty cast list is 64 sprites in the parking lot.

The fast lane

How does a game fill it? Sixty-four moving things per frame through a one-byte-at-a-time register would eat the whole vblank. So the console installed a fire hose: the game lays out all 256 bytes in ordinary RAM — a private copy it can scribble on all frame long — then writes the page number to $4014, and the hardware copies the entire page into OAM in one gulp. Chase does exactly this on every single NMI: rebuild the roster in RAM at $0200, then $4014, done.

Painting the cast is chapter 13’s tile decoding wearing three new rules. /// Paint the 64 sprites over the finished background, roster's back
/// to roster's front, so sprite 0 wins every overlap.
fn render_sprites(cpu: &Cpu, buffer: &mut [u32]) {
    let ppu = &cpu.bus.ppu;
    let chr = &cpu.bus.cartridge.chr_rom;

    // PPUCTRL bit 3: which half of the album holds sprite tiles.
    // Games flip this bit to animate their whole cast at once.
    let table = if ppu.ctrl & 0b0000_1000 != 0 { 256 } else { 0 };

    for sprite in ppu.oam.chunks(4).rev() {
        let (top, tile, attributes, left) =
            (sprite[0], sprite[1], sprite[2], sprite[3]);

        // Parking a sprite at the bottom edge is the "I'm not here"
        // convention: anything from $EF down starts past row 239.
        if top >= 0xEF {
            continue;
        }

        let pixels = ppu::decode_tile(chr, table + tile as usize);
        let palette = sprite_palette(ppu, attributes);

        for (row, line) in pixels.iter().enumerate() {
            // Hardware draws every sprite one row below its stored
            // Y — games store "top minus one" and know it.
            let y = top as usize + 1 + row;
            if y >= HEIGHT {
                break;
            }

            for (col, &value) in line.iter().enumerate() {
                // Color 0 is a hole: the scenery shows through.
                if value == 0 {
                    continue;
                }
                let x = left as usize + col;
                if x >= WIDTH {
                    break;
                }
                let crayon = palette[value as usize];
                buffer[y * WIDTH + x] = ppu::SYSTEM_PALETTE[crayon as usize];
            }
        }
    }
}

/// to keep the indexing honest — sprites never paint with it.
fn sprite_palette(ppu: &ppu::Ppu, attributes: u8) -> [u8; 4] {

    [

For the curious

Our frame is 29,780 cycles; a real NTSC frame is 29,780 and a half — the PPU’s 341 dots per line don’t divide by 3. The half-cycle wobble is why long recordings of real consoles slowly drift against a stopwatch, and why serious emulators run the PPU dot by dot instead of letting the CPU lead. Beep boop

Everything the machine has ever said, it has said through the window. Its other organ of speech has been sitting silent at $4000: the APU, the Audio Processing Unit, five voices on one chip. What sound is

A speaker is a little drum on a wire: push current through the coil and the cone leans out, cut it and the cone falls back. Do that a few hundred times a second and the air wobbles; the wobble is a tone. Pitch is how often the cone moves; loudness is how far. A flute pushes the air in smooth hills. This console can’t afford hills — its cone has two positions, out and back, and the only choice left is how long to stay out each cycle. That choice is called duty, and the chip offers four:

The shapes sound distinct enough that composers treat them as instruments: the fat square for lead melodies, the thinner ones for accompaniment with bite. Between duty and loudness, a pulse voice needs exactly one more fact — how fast to repeat the shape — and that comes from an 11-bit countdown called the timer: the chip walks one step of the shape every 2 × (timer + 1) CPU cycles. Small timer, fast walk, high note. Pitch on this machine is literally measured in CPU cycles.

/// One pulse voice: a shape, a loudness, a pitch — and where in its
/// cycle it currently stands.
pub struct Pulse {
    /// Which DUTY row to sing.
    duty: usize,

    /// Loudness, 0 to 15, straight from the register.
    volume: u8,

    /// The 11-bit countdown that sets the pitch: the chip walks one
    /// step of the shape every 2 x (timer + 1) CPU cycles.
    timer: u16,

    /// Where in the eight-step cycle the voice is, as a fraction
    /// 0 to 1 — the one field that moves while a note is held.
    phase: f32,
}

impl Pulse {
    fn new() -> Pulse {
        Pulse {
            duty: 0,
            volume: 0,
            timer: 0,
            phase: 0.0,
        }
    }

    /// $4000 / $4004 — shape and loudness. (The middle bits select
    /// the envelope and length-counter behaviors; both of our games
    /// keep them pinned to "constant volume, never cut me off", so
    /// constant volume is what we build.)
    fn write_control(&mut self, value: u8) {
        self.duty = (value >> 6) as usize;
        self.volume = value & 0x0F;
    }

    /// $4002 / $4006 — the timer's low eight bits. Melodies ride this
    /// register: small nudges here bend the pitch between notes.
    fn write_timer_low(&mut self, value: u8) {
        self.timer = (self.timer & 0x0700) | value as u16;
    }

    /// $4003 / $4007 — the timer's top three bits. Writing here also
    /// restarts the shape from step zero, so games save this register
    /// for genuine pitch jumps.
    fn write_timer_high(&mut self, value: u8) {
        self.timer = (self.timer & 0x00FF) | (((value & 0x07) as u16) << 8);
        self.phase = 0.0;
    }

    /// The note being sung, in hertz: sixteen timer-loads of the
    /// timer per full eight-step cycle.
    fn frequency(&self) -> f32 {
        CPU_HZ / (16.0 * (self.timer as f32 + 1.0))
    }

    /// Sing one sample: the volume, or nothing, says the shape. A
    /// timer under 8 would whistle above 14 kHz — the real chip mutes
    /// it there, and so do we.
    fn sample(&mut self, sample_rate: f32) -> u8 {
        if self.volume == 0 || self.timer < 8 {
            return 0;
        }

        let step = (self.phase * 8.0) as usize & 7;
        self.phase = (self.phase + self.frequency() / sample_rate).fract();
        DUTY[self.duty][step] * self.volume
    }
}

The register layout deserves a squint. $4002 holds the timer’s low eight bits alone, and melodies live there: FamiTone — the music engine both our games ship — nudges it every frame to bend between notes. $4003 holds the top three bits and restarts the shape, so engines only touch it for real jumps. And the phase is our first f32 doing real work: at 44,100 samples a second, a 440 Hz note advances the shape about one percent per sample, and a fraction is the honest way to keep count.

/// The sound chip: its two pulse voices and the on/off switchboard.
pub struct Apu {
    pulse1: Pulse,
    pulse2: Pulse,

    /// $4015 — one enable bit per voice; bits 0 and 1 are the pulses.
    enabled: u8,
}

impl Apu {
    pub fn new() -> Apu {
        Apu {
            pulse1: Pulse::new(),
            pulse2: Pulse::new(),
            enabled: 0,
        }
    }

    /// A write to any sound register. The two pulses answer; the
    /// other three voices — triangle bass, noise drums, sample
    /// playback — are Part II's, and their registers fall through
    /// politely until then.
    pub fn write(&mut self, address: u16, value: u8) {
        match address {
            0x4000 => self.pulse1.write_control(value),
            0x4002 => self.pulse1.write_timer_low(value),
            0x4003 => self.pulse1.write_timer_high(value),
            0x4004 => self.pulse2.write_control(value),
            0x4006 => self.pulse2.write_timer_low(value),
            0x4007 => self.pulse2.write_timer_high(value),
            0x4015 => self.enabled = value,
            _ => {}
        }
    }

/// The pulse pair's mixing curve, from the chip's own resistor
/// ladder. It is NOT a plain sum: two loud voices together come out
/// quieter than twice one voice, which keeps the mix from clipping.
fn mix(pulse1: u8, pulse2: u8) -> f32 {
    let sum = (pulse1 + pulse2) as f32;
    if sum == 0.0 {
        return 0.0;
    }

    95.88 / (8128.0 / sum + 100.0)
}

/// The speaker's end of the machine: the stream that plays (sound
/// stops the moment it is dropped), the queue of samples on their
/// way out, and the rate the device wants them at.
struct Speaker {
    _stream: cpal::Stream,
    queue: Arc<Mutex<VecDeque<f32>>>,
    sample_rate: f32,
}

impl Speaker {
    /// One frame of sound to match a frame of picture: a sixtieth of
    /// a second of samples, sung from wherever the channels stand.
    /// The cap keeps a slow frame from letting the queue — and the
    /// lag behind the picture — grow forever.
    fn sing_a_frame(&self, apu: &mut apu::Apu) {
        let mut queue = self.queue.lock().unwrap();
        if queue.len() < self.sample_rate as usize / 15 {
            for _ in 0..self.sample_rate as usize / 60 {
                queue.push_back(apu.sample(self.sample_rate));
            }
        }
    }
}

/// Ask the operating system for the speaker, and start it playing
/// from its queue.
fn start_audio() -> Option<Speaker> {
    let device = cpal::default_host().default_output_device()?;
    let config = device.default_output_config().ok()?;
    let sample_rate = config.sample_rate().0 as f32;
    let channels = config.channels() as usize;

    let queue = Arc::new(Mutex::new(VecDeque::new()));
    let feed = Arc::clone(&queue);

    // The sound card calls this little function whenever it wants
    // more sound — from its own thread, on its own schedule. Whatever
    // is queued gets played; an empty queue plays silence, because a
    // speaker with nothing to say should say nothing.
    let stream = device
        .build_output_stream(
            &config.into(),
            move |out: &mut [f32], _: &cpal::OutputCallbackInfo| {
                let mut queue = feed.lock().unwrap();
                for frame in out.chunks_mut(channels) {
                    let sample = queue.pop_front().unwrap_or(0.0);
                    for speaker in frame {
                        *speaker = sample;
                    }
                }
            },
            |error| eprintln!("the speaker complained: {error}"),
            None,
        )
        .ok()?;

    stream.play().ok()?;
    Some(Speaker { _stream: stream, queue, sample_rate })
}
